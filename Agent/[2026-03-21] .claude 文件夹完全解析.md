## 一份关于 CLAUDE.md、自定义命令、skills、agents 和权限配置的完整指南，以及如何正确设置它们。

大多数 Claude Code 用户把 .claude 文件夹当成黑盒。他们知道它的存在，也见过它出现在项目根目录下，但从没打开过，更别说理解里面每个文件的作用了。**这其实是个很大的遗漏。**.claude 文件夹是 Claude 在你项目中行为方式的**控制中心**。它保存着你的指令、自定义命令、权限规则，甚至是 Claude 跨会话的记忆。一旦你搞清楚哪些东西放在哪里、为什么这样放，就能把 Claude Code 调教成完全符合团队需求的样子。本文将完整拆解这个文件夹的结构，从你每天都会用到的文件，到那些设置一次就再也不用管的配置。

## 两个文件夹，不是一个

在深入之前，有一点值得先说清楚：实际上存在**两个** .claude 目录，不是一个。第一个在项目内部，第二个在你的 home 目录下：

## CLAUDE.md：Claude 的使用说明书

这是整个系统中**最重要的文件**。当你启动一个 Claude Code 会话时，它首先读取的就是 CLAUDE.md。它会把内容直接加载到系统提示词中，并在整个对话过程中持续参考。简单来说：**你在 CLAUDE.md 里写什么，Claude 就照做。**如果你告诉 Claude 始终先写测试再写实现，它就会这么做。如果你说"不要用 console.log 处理错误，始终使用自定义 logger 模块"，它每次都会遵守。在项目根目录放一个 CLAUDE.md 是最常见的用法。但你也可以在 ~/.claude/CLAUDE.md 放一个全局配置，适用于所有项目；甚至可以在子目录里放一个，设置特定文件夹的规则。Claude 会读取所有这些文件并合并它们。

**CLAUDE.md 控制在 200 行以内。** 超过这个长度会开始消耗过多上下文，Claude 对指令的遵循度反而会下降。

大约 20 行，就能提供 Claude 在这个代码库中高效工作所需的全部信息，不需要反复确认。

## CLAUDE.local.md：个人覆盖配置

有时候你有一些只属于自己的偏好，而不是整个团队的。也许你更喜欢另一个测试运行器，或者你希望 Claude 总是用特定的模式打开文件。在项目根目录创建 CLAUDE.local.md 就行。Claude 会在读取主 CLAUDE.md 的同时读取它，而且它会被自动加入 gitignore，你的个人设置永远不会进入代码仓库。

## rules/ 文件夹：可扩展的模块化指令

CLAUDE.md 在单个项目中表现很好。但当团队规模扩大后，你会发现 CLAUDE.md 膨胀到了 300 行，没人维护，也没人看。**rules/ 文件夹就是解决这个问题的。**.claude/rules/ 里的每个 markdown 文件都会和 CLAUDE.md 一起自动加载。与其维护一个巨大的文件，不如按关注点拆分指令：每个文件保持专注，便于更新。负责 API 规范的团队成员编辑 api-conventions.md，负责测试标准的人编辑 testing.md，互不干扰。

### 路径作用域规则

真正强大的地方在于**路径作用域规则**。在规则文件中添加 YAML frontmatter，它就只会在 Claude 处理匹配文件时激活：当 Claude 在编辑 React 组件时，这个文件不会被加载。只有当它在 src/api/ 或 src/handlers/ 目录下工作时才会加载。没有 paths 字段的规则会无条件加载，每次会话都生效。

当你的 CLAUDE.md 开始显得臃肿时，这就是正确的演进方式。

## commands/ 文件夹：自定义斜杠命令

Claude Code 开箱即带一些内置的斜杠命令，比如 /help 和 /compact。commands/ 文件夹让你可以添加自己的命令。你放入 .claude/commands/ 的每个 markdown 文件都会变成一个斜杠命令。

[图片]

这是一个简单的例子。创建 .claude/commands/review.md：在 Claude Code 中运行 /project:review，它会自动把真实的 git diff 注入到提示词中，在 Claude 看到之前。! 反引号语法会执行 shell 命令并嵌入输出。这才是让这些命令真正有用的关键，而不仅仅是保存的文本。

### 向命令传递参数

使用 $ARGUMENTS 来传递命令名后面的文本：运行 /project:fix-issue 234 会把 issue 234 的内容直接注入到提示词中。

## skills/ 文件夹：按需调用的可复用工作流

你已经了解了 commands 的工作方式。Skills 表面上看起来类似，但触发机制有本质区别。

[图片]

**Skills vs Commands 的核心区别**：Skills 是 Claude 可以**自行调用**的工作流——当任务匹配 skill 的描述时，不需要你输入斜杠命令就能触发。Commands 等你来调用，Skills 则监听对话并在合适的时机主动介入。

每个 skill 放在独立的子目录中，包含一个 SKILL.md 文件。SKILL.md 使用 YAML frontmatter 来描述何时使用：当你说"检查这个 PR 有没有安全问题"时，Claude 读取描述，识别到匹配，然后自动调用这个 skill。你也可以通过 /security-review 显式调用它。与 commands 的关键区别：**skills 可以在旁边打包辅助文件**。上面的 @DETAILED_GUIDE.md 引用了一个和 SKILL.md 放在一起的详细文档。Commands 是单个文件，Skills 是完整的包。个人 skills 放在 ~/.claude/skills/，在所有项目中可用。

## settings.json：权限和项目配置

.claude/ 中的 settings.json 文件控制 Claude 能做什么、不能做什么。你在这里定义 Claude 可以运行哪些工具、可以读取哪些文件，以及在运行某些命令前是否需要征求许可。

和 CLAUDE.local.md 同理。创建 .claude/settings.local.json 来存放你不想提交的权限变更，它会被自动加入 gitignore。

## 实战起步指南

如果你从零开始，以下是一条行之有效的路径：

**第一步**：在 Claude Code 中运行 /init。它会通过读取你的项目自动生成一个初始 CLAUDE.md。把它精简到核心要素。**第二步**：添加 .claude/settings.json，配置适合你技术栈的 allow/deny 规则。至少要允许你的运行命令，禁止读取 .env。**第三步**：为你最常用的工作流创建一两个命令。代码审查和 issue 修复是很好的起点。**第四步**：随着项目增长，CLAUDE.md 开始变得臃肿时，把指令拆分到 .claude/rules/ 文件中。在合适的地方按路径设置作用域。**第五步**：在 ~/.claude/CLAUDE.md 中添加你的个人偏好。比如"始终先写类型定义再写实现"或"优先使用函数式风格而不是类"。

对于 95% 的项目来说，这些就够了。Skills 和 agents 是当你有值得打包的复杂重复工作流时才需要的。

### 核心洞察

## .claude 文件夹本质上是一套**协议**，用来告诉 Claude 你是谁、你的项目做什么、它应该遵循什么规则。你定义得越清晰，花在纠正 Claude 上的时间就越少，它花在做有用工作上的时间就越多。**CLAUDE.md 是你杠杆效应最大的文件。先把它搞对，其他都是优化。**从小处着手，逐步打磨，像对待项目中的其他基础设施一样对待它：一旦设置好了，就能天天产生回报。
