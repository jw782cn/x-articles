# [2026-04-09] Agent 优先产品工程的黄金法则

很多公司在构建 Agent 能力时，只是把它当成一个附加功能。

这是一个错误。

如今的 Agent 更像是一种全新的形态——它是一个交互层，介于你的产品和用户之间：

[图片]

这意味着你需要把 Agent 当作主要界面来构建，而不是事后补丁。

如果做得好，这会为你的产品打开全新的可能性空间，比如自主工作和异步流程。

如果做得差，你会因为缓慢、bug 频出的体验和错误的结果而失去用户信任。

我们在这方面吃过大亏，过去一年里把 AI 架构推翻重做了两次。现在，我们的 Agent 和 MCP 每天有 6000 多活跃用户。

以下是我们一路走来总结出的 Agent 优先产品工程的黄金法则。

## 1. 让 Agent 能做用户能做的一切

如果人类能在你的产品中做某件事，Agent 也应该能做到。

举个例子，假设你让一个 Agent 为新定价页面设置一个 A/B 测试。

Agent 会使用 PostHog MCP 来创建 feature flag，创建实验，将实验关联到刚创建的 flag，并设置 insight 和指标。

现在想象一下，如果"创建实验"这个工具缺失了——仅仅因为我们还没来得及做。Agent 创建了 flag 和 insight，但不得不停下来，让你去 PostHog 里手动创建实验，然后把实验 ID 粘贴回来。

这很烦人，而且完全违背了初衷。

Agent 的价值在于减少完成任务所需的时间、注意力和专业知识。如果你的产品不能给 Agent 和用户同等的能力，你就永远被人工环节限制住。

当然，有些场景下要求人工介入是合理的，比如处理敏感数据。但这些应该是刻意的例外，而不是无意的遗漏。

## 2. 在 Agent 的抽象层级上与它对话

要构建 Agent 优先的体验，你必须找到 Agent 已经能最好地进行推理的语义层，然后在那个层级上与它对接。

这能节省大量的 context（一种宝贵的资源），但好处不仅仅是实用层面的，而是根本性的。你产品的 Agent 接口越"原始"，你解锁的创造潜力就越大。

想象给一个孩子生日送一套乐高。如果轮胎和车轴已经粘在一起了，他们就只会造汽车、卡车和飞机——所有人都见过的交通工具。

如果零件是分开的，他们就能自由组合，造出摩托车、轮胎秋千、雪橇，以及谁知道什么其他东西。

### 实践中是什么样的

在旧版 MCP 中，要回答"上周注册量为什么下降了？"，Agent 需要进行四次独立调用：projects-get、insight-get 和 insight-query（两次）。

get-insight 或 get-funnel 对在 PostHog UI 中导航的人类来说可能有意义，但对 Agent 来说，这只是不必要的翻译步骤。

## 3. 前置通用上下文

在 AI 的早期阶段，开发者不得不把所有东西都预先加载给 Agent，以弥补较小的 context window 和较弱的模型能力。

但随着技术不断进步，出现了一种新趋势：尽可能移除 context，信任模型自己搞定剩下的。

这对通用 Agent 有效，因为它们本就被设计为灵活应变的。Anthropic 无法预测每个人用 Claude 做什么。

但如果你是为自己特定产品构建 Agent 体验，问题空间要小得多。你已经知道关键场景、工具和用例。

所以对于产品工程师来说，你可以找到一个平衡点：前置加载你知道每次会话都需要的内容，其余的延迟加载。

## 5. 像对待真实用户一样对待 Agent

在传统软件中，即使用户行为不可预测，代码本身是可预测的。而有了 AI，你失去了这种稳定性——相同的输入不再产生相同的输出。

这意味着经典的测试方法会留下空白，所以你需要新的方式来捕捉自动化测试再也抓不住的问题。

你需要像对待用户一样对待 Agent。与它们交谈，建立对它们的共情，培养对它们需求的直觉。

这能帮助你像它们一样看待你的产品，熟悉它们所有的交互模式和怪癖。

**核心观点**：构建 Agent 优先的产品需要五个关键原则——让 Agent 拥有与用户同等的能力、在正确的抽象层级暴露接口、前置加载关键上下文、像培训优秀员工而非写操作手册一样编写 skill、以及像对待真实用户一样测试和理解 Agent 的行为。这不是一个附加功能，而是一种需要从根本上重新思考产品设计的全新交互范式。
