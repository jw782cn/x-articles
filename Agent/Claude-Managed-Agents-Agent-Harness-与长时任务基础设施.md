Lance Martin（Anthropic）在推文串中分享了他参与撰写的 Anthropic 工程博客文章，讨论了 Claude Managed Agents 中关于 agent harness 和长时任务基础设施的设计思考。以下为博客全文翻译。

---

开始使用 Claude Managed Agents，请参考我们的文档。

工程博客中一个持续讨论的话题是：如何构建有效的 agent，以及如何为长时运行的工作设计 harness。贯穿这些工作的一个共同主线是：harness 编码了关于 Claude 无法独立完成什么的假设。然而，这些假设需要被经常质疑，因为随着模型的改进，它们可能会过时。

举一个例子：在之前的工作中我们发现，Claude Sonnet 4.5 会在感觉到上下文限制接近时过早地结束任务——这种行为有时被称为"上下文焦虑"。我们通过在 harness 中添加上下文重置来解决这个问题。但当我们对 Claude Opus 4.5 使用相同的 harness 时，发现这种行为已经消失了。重置功能变成了累赘。

我们预期 harness 将持续演进。因此我们构建了 Managed Agents：一个在 Claude Platform 上托管的服务，通过一小组接口代替你运行长时 agent，这些接口旨在比任何特定的实现都更持久——包括我们今天运行的那些实现。

构建 Managed Agents 意味着要解决计算领域中的一个老问题：如何为"尚未构思出的程序"设计系统。几十年前，操作系统通过将硬件虚拟化为抽象概念——进程、文件——来解决这个问题，这些抽象足够通用，可以服务于尚不存在的程序。抽象比硬件更持久。 read() 命令不关心它访问的是 1970 年代的磁盘组还是现代 SSD。上层的抽象保持稳定，而底层的实现可以自由变化。

Managed Agents 遵循相同的模式。我们虚拟化了 agent 的组件：session（所有发生事件的追加日志）、harness（调用 Claude 并将 Claude 的工具调用路由到相关基础设施的循环）和 sandbox（Claude 可以运行代码和编辑文件的执行环境）。这允许每个组件的实现被替换而不干扰其他组件。我们对这些接口的形态有明确的主张，但对它们背后运行的内容不做限定。

## 不要养宠物

我们最初将所有 agent 组件放入一个容器中，这意味着 session、agent harness 和 sandbox 共享一个环境。这种方式有好处，包括文件编辑是直接的系统调用，而且不需要设计服务边界。

但通过将一切耦合到一个容器中，我们遇到了一个老的基础设施问题：我们养了一只宠物。在"宠物 vs 牲畜"的类比中，宠物是你不能承受失去的、被精心照料的个体，而牲畜是可替换的。在我们的情况中，服务器变成了那只宠物；如果容器崩溃，session 就丢失了。如果容器没有响应，我们必须把它"治好"。

"治疗"容器意味着调试无响应的卡住会话。我们唯一的窗口是 WebSocket 事件流，但它无法告诉我们故障出现在哪里，这意味着 harness 中的 bug、事件流中的丢包或容器下线，表现都是一样的。要弄清楚出了什么问题，工程师必须在容器内打开 shell，但因为那个容器通常也包含用户数据，这种方法本质上意味着我们失去了调试能力。

第二个问题是，harness 假设 Claude 工作的内容都在容器内。当客户要求我们将 Claude 连接到他们的虚拟私有云时，他们要么必须将网络与我们对等连接，要么在自己的环境中运行我们的 harness。一个嵌入 harness 中的假设在我们想要连接到不同基础设施时变成了问题。

解决方案：将"大脑"（Claude 及其 harness）与"双手"（执行操作的 sandbox 和工具）以及"session"（会话事件日志）解耦。每个组件成为一个对其他组件做最少假设的接口，可以独立失败或替换。

Harness 离开容器。 将大脑从双手解耦意味着 harness 不再存在于容器内。它调用容器的方式与调用其他工具一样：execute(name, input) → string。容器变成了牲畜。如果容器死了，harness 将故障作为工具调用错误捕获并传回给 Claude。如果 Claude 决定重试，可以用标准配方重新初始化一个新容器：provision({resources})。我们不再需要把崩溃的容器"治好"。

从 harness 故障中恢复。 Harness 也变成了牲畜。因为 session 日志在 harness 之外，harness 中没有什么需要在崩溃中存活。当一个 harness 失败时，可以用 wake(sessionId) 重启一个新的，使用 getSession(id) 取回事件日志，从最后一个事件恢复。在 agent 循环期间，harness 用 emitEvent(id, event) 写入 session 以保持事件的持久记录。

安全边界。 在耦合设计中，Claude 生成的任何不受信代码都在与凭证相同的容器中运行——因此 prompt injection 只需要说服 Claude 读取自己的环境。一旦攻击者获得了这些 token，他们可以生成新的不受限制的会话并将工作委托给它们。范围限制是一个明显的缓解措施，但这编码了一个关于 Claude 用有限 token 能做什么的假设——而 Claude 正在变得越来越聪明。结构性修复是确保 token 永远不能从 Claude 生成代码运行的 sandbox 中被访问到。

我们使用了两种模式来确保这一点。认证可以与资源绑定或存储在 sandbox 外的保险库中。对于 Git，我们在 sandbox 初始化期间使用每个仓库的访问 token 来 clone 仓库并将其接入本地 git remote。Git push 和 pull 在 sandbox 内工作，而 agent 本身永远不会接触到 token。对于自定义工具，我们支持 MCP 并将 OAuth token 存储在安全保险库中。Claude 通过专用代理调用 MCP 工具；这个代理接收与 session 关联的 token。代理然后从保险库获取相应的凭证并调用外部服务。Harness 永远不会接触到任何凭证。

## Session 不是 Claude 的上下文窗口

长时任务经常超出 Claude 上下文窗口的长度，而解决这个问题的标准方法都涉及关于保留什么的不可逆决策。我们在之前关于上下文工程的工作中探索了这些技术。例如，compaction 让 Claude 保存其上下文窗口的摘要，memory 工具让 Claude 将上下文写入文件，实现跨会话的学习。这可以与 context trimming 配对使用，后者选择性地移除 token，如旧的工具结果或思考块。

但选择性保留或丢弃上下文的不可逆决策可能导致失败。很难知道未来的轮次需要哪些 token。 如果消息被 compaction 步骤转换，harness 会从 Claude 的上下文窗口中移除被压缩的消息，而这些消息只有在被存储的情况下才能恢复。之前的工作已经探索了通过将上下文存储为上下文窗口之外的对象来解决这个问题的方法。例如，上下文可以是 REPL 中的一个对象，LLM 通过编写代码来过滤或切片来程序化地访问它。

在 Managed Agents 中，session 提供了同样的好处，作为存在于 Claude 上下文窗口之外的上下文对象。但与存储在 sandbox 或 REPL 中不同，上下文被持久存储在 session 日志中。接口 getEvents() 允许大脑通过选择事件流的位置切片来查询上下文。这个接口可以灵活使用，允许大脑从上次停止阅读的地方继续、在特定时刻之前回退几个事件来查看前因，或在特定操作之前重新读取上下文。

获取的事件在传递到 Claude 上下文窗口之前，也可以在 harness 中被转换。这些转换可以是 harness 编码的任何内容，包括上下文组织以实现高 prompt cache 命中率和上下文工程。我们将可恢复的上下文存储（在 session 中）和任意上下文管理（在 harness 中）分开关注，因为我们无法预测未来模型需要什么特定的上下文工程。 接口将上下文管理推入 harness，只保证 session 是持久的且可供查询。

## 多个大脑，多双手

### 多个大脑

将大脑从双手解耦解决了我们最早的一个客户投诉。当团队想要 Claude 针对自己 VPC 中的资源工作时，唯一的路径是将他们的网络与我们对等连接，因为持有 harness 的容器假设每个资源都在它旁边。一旦 harness 不再在容器中，这个假设就消失了。同样的变化带来了性能回报。当我们最初将大脑放在容器中时，这意味着多个大脑需要同样多的容器。对于每个大脑，在该容器被配置之前不能进行推理；每个会话预先支付了完整的容器设置成本。每个会话——即使是那些永远不会触及 sandbox 的——都必须 clone 仓库、启动进程、从我们的服务器获取待处理事件。

性能提升：通过解耦大脑和双手，容器仅在需要时通过工具调用 execute(name, input) → string 按需配置。不需要容器的会话无需等待。推理可以在编排层从 session 日志中拉取待处理事件后立即开始。使用这种架构，p50 TTFT 下降约 60%，p95 下降超过 90%。

扩展到多个大脑只意味着启动多个无状态 harness，仅在需要时连接到双手。

### 多双手

我们还希望能够将每个大脑连接到多双手。在实践中，这意味着 Claude 必须推理多个执行环境并决定将工作发送到哪里——这比在单个 shell 中操作更难的认知任务。我们最初将大脑放在单个容器中，因为早期模型不具备这种能力。随着智能的扩展，单个容器反而成为了限制：当该容器失败时，我们丢失了大脑正在接触的每只手的状态。

将大脑从双手解耦使每只手成为一个工具，execute(name, input) → string：一个名称和输入进入，一个字符串返回。这个接口支持任何自定义工具、任何 MCP 服务器，以及我们自己的工具。 Harness 不知道 sandbox 是容器、手机还是 Pokémon 模拟器。因为没有手与任何大脑耦合，大脑可以将手传递给彼此。

## 结论

我们面临的挑战是一个古老的：如何为"尚未构思出的程序"设计系统。操作系统通过将硬件虚拟化为足够通用的抽象来支持尚不存在的程序，已经持续了几十年。通过 Managed Agents，我们旨在设计一个能够容纳围绕 Claude 的未来 harness、sandbox 或其他组件的系统。

Managed Agents 是一个同样精神的 meta-harness，对 Claude 未来需要的特定 harness 不做限定。相反，它是一个具有通用接口的系统，允许许多不同的 harness。例如，Claude Code 是一个优秀的 harness，我们广泛用于各种任务。我们也展示了针对特定任务的 agent harness 在狭窄领域中表现出色。Managed Agents 可以容纳这些中的任何一个，随着时间的推移匹配 Claude 的智能。

Meta-harness 设计意味着对 Claude 周围的接口持有明确的主张：我们预期 Claude 将需要操纵状态（session）和执行计算（sandbox）的能力。我们也预期 Claude 将需要扩展到多个大脑和多双手的能力。我们设计了接口，使这些可以在长时间范围内可靠且安全地运行。但我们不对 Claude 将需要的大脑或手的数量或位置做出假设。

核心观点：Managed Agents 的核心设计哲学是将 agent 的组件（大脑/harness、双手/sandbox、session/日志）解耦为独立的、可替换的抽象接口，就像操作系统将硬件虚拟化为进程和文件一样。这种 meta-harness 架构带来了三大收益：容错性（组件可独立失败和恢复）、安全性（凭证与执行环境隔离）、性能（TTFT p50 降低 60%，p95 降低 90%）。最重要的是，它为未来尚未构思出的 agent 模式预留了空间。
