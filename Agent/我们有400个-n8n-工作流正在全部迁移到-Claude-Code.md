# [2026-04-07] 我们有 400 个 n8n 工作流，正在全部迁移到 Claude Code

原文链接：We Had 400 n8n Workflows. We're Migrating Every One to Claude Code. by @aryanXmahajan1.2万阅读 | 109点赞 | 292收藏

六个月前，我们在 n8n 上撞了墙。

不是因为 n8n 不好。它确实是有史以来最好的自动化工具之一。我们用它为多个客户连接了几十个系统，在小规模场景下它上手快、也方便给客户演示。

但我们当时跨客户运行着超过 400 个工作流。线索enrichment 管道要处理数千条记录。内容爬取系统同时从数百个 Instagram 账号和竞品博客拉取数据。多步骤外呼序列在每个节点都有分支逻辑、回退路由和条件评分。

到了这个量级，n8n 就开始跟你对着干了。

一个 API 调用失败就会在整个同步工作流中产生连锁反应。在 50 条记录上好好的错误处理，到了 5000 条就悄无声息地崩了。自托管意味着每个意外的故障模式都得你自己调试，而且完全看不到执行过程中到底发生了什么。当你需要更多并发执行能力时，还没来得及测试架构能不能撑住，就得先升级套餐。

我们做出了迁移的决定。以下是我们具体的做法。

## 为什么 n8n 在大规模场景下会崩（说实话版）

n8n 是一个可视化工作流构建器。可视化抽象在低复杂度下是它最大的优势，在高复杂度下则成了最大的负担。

当你在可视化画布上连接 30 个节点时，每个节点都有自己的配置面板，数据按顺序从一个传到下一个，这套抽象是撑得住的。你能看到整个流程，能追踪数据的走向，能单独测试每个节点。

当你运行的工作流要处理 3000 条线索，每条都要经过 Apollo enrichment、Apify LinkedIn 爬取、Claude AI 评分、Airtable 写入和 Slack 通知时，这套抽象就成了负担。原因如下：

默认同步执行。 如果一个 10 节点工作流中第 4 个节点的 API 调用失败了，整个执行就停了。剩下的 6 个节点永远不会运行。你在执行日志里看到一个报错，而那些失败时正在处理中的记录，数据全部丢失。重试逻辑是可以做的，但需要在每个可能失败的点都包上显式的错误处理节点，在一个 30 节点的工作流里，这意味着巨大的结构性开销。

错误可见性有限。 n8n 的执行日志会告诉你哪个节点失败了，但不会告诉你失败时外部系统处于什么状态。Airtable 的写入在 Slack 通知失败之前完成了吗？写了一半的记录吗？如果你没有在 n8n 之外实现自定义的错误追踪，那你就是在盲调。

容量扩展需要升级套餐。 在 n8n Cloud 上进行高并发处理需要升级到更高的套餐层级才能提升并发上限。自托管 n8n 解决了并发问题，但又重新引入了基础设施维护的负担，而且还是解决不了错误可见性的问题。

工作流维护会随时间累积。 我们有些工作流是 14 个月前建的，没人完全记得它们是怎么运作的。原始逻辑编码在可视化画布里。要改什么东西，你得打开画布、追踪流程、找到节点、修改配置，然后祈祷你没有在某个没测过的分支里引入一个隐蔽的 bug。400 个工作流、12 个客户，这是一个真实的运维问题。

Claude Code 把这四个问题全解决了。不是因为它有什么魔法，而是因为你能读、能测、能版本控制、能扩展的代码，本质上就比同样逻辑的可视化抽象更容易维护。

## 迁移架构：我们是怎么想的

在动手碰任何工作流之前，我们先定义了要迁移到什么样的架构。

每个迁移后系统的目标架构有四层：

后端服务。 Python 或 Node.js，部署在 Render 上。所有业务逻辑都在这里。API 集成、数据处理、AI 调用、错误处理、重试逻辑。以前是 n8n 节点的东西，现在是一个正经代码库里的函数。

前端界面。 部署在 Vercel 上。每个客户都有一个真正的 dashboard。状态视图、运行日志、手动触发按钮、错误报告、设置面板。n8n 没有面向客户的界面。一个真正的前端能把我们构建的东西的感知价值提升十倍。客户不再把它当作"一个自动化"，而是开始把它当作"他们的系统"。

GitHub 仓库。 一切都在版本控制里。每次修改都是一个 commit。每次部署都由 push 触发。回滚只需几秒。多个团队成员可以同时在同一个系统上工作而不会互相冲突。

MCP 连接到我们的项目管理层。 每个客户系统都通过 MCP 连接回我们的内部工具。我们在 Plane 里追踪工作流运行情况、错误率和里程碑进度，对照 PRD 来看。系统会自己报告自己的状态。

这就是我们每个 n8n 工作流迁移的目标。接下来的内容讲的是如何到达那里。

## 阶段 1：导出 n8n 工作流

n8n 工作流是 JSON 格式的。这是这次迁移的第一个优势。

我们曾经构建的每个工作流都可以导出为一个结构化的 JSON 文件，包含每个节点、每个连接、每个配置。导出操作可以直接在 n8n 编辑器的顶部导航菜单中完成，自托管实例也可以通过 n8n CLI 以编程方式导出。

对于我们这 400 个工作流的迁移，我们没有手动导出。我们使用 n8n 的公开 REST API 以编程方式拉取了所有工作流。n8n API 需要一个 API key，你可以在 n8n 实例设置中生成。拿到 key 之后，一个脚本就能拉取你实例中的所有工作流，并把每个都写成本地 JSON 文件。

导出后我们的文件夹结构：

```
/n8n-workflows
  /client-name-1
    workflow-lead-enrichment.json
    workflow-outbound-sequence.json
    workflow-slack-notifications.json
  /client-name-2
    workflow-content-scraping.json
    workflow-competitor-analysis.json
  /client-name-3
    ...

```

每个客户一个文件夹。该客户的所有工作流都在里面。这个文件夹结构很重要，因为它会成为 Claude Code 迁移会话的上下文边界。

我们在把导出的 JSON 放入仓库之前，会先清除凭证值。导出文件包含凭证名称和 ID，但不包含实际的密钥。不过我们还是会清理 JSON，把所有认证头替换为占位符，并记录重建后的系统需要配置哪些环境变量才能运行。

## 阶段 2：设置 Claude Code 会话

这是大多数人犯错的地方：他们把所有 400 个工作流一股脑丢进一个 Claude Code 会话里，然后让它把所有东西都迁移了。

不要这样做。即使有百万 token 的上下文窗口，把 400 个工作流 JSON 加上所有客户文档塞进一个会话，产出的结果会是混乱且不一致的。每个客户开一个会话，保持上下文边界的清晰。

以下是每个客户的 Claude Code 会话中应该包含的内容：

该客户的工作流 JSON 文件。 全部导入到客户的文件夹中。Claude Code 把这些作为现有系统功能的事实来源来阅读。

客户的入职文档。 ICP 定义、漏斗结构、他们使用的工具栈、他们期望每个系统输出什么。

正在重建的系统的 PRD。 完整的规格说明，包括目标架构、UI 层、API 集成和错误处理需求。

提案和合同。 去除所有个人身份信息之后的版本。Claude Code 需要理解约定的范围。如果某个功能不在合同里，就不构建它。

客户分享的相关案例研究和资源。 特别是对于内容类系统，这很重要。如果我们在重建一个竞品分析系统，Claude Code 需要理解对这个客户来说"好的输出"长什么样。

客户系统的 API key 放在项目根目录的 .env 文件里。 Claude Code 从那里读取。永远不要硬编码，永远不要粘贴到对话里。

CLAUDE.MD 包含架构决策：用什么语言、什么框架、部署到哪里、代码风格规范是什么、异步操作和错误处理使用什么模式。

## 阶段 3：上下文建立（大多数人跳过的步骤）

在让 Claude Code 构建任何东西之前，我会花 20 到 30 分钟建立完整的上下文。

"这是客户 X 的 n8n 工作流文件。读一下。告诉我你理解每个工作流在做什么，数据流是什么样的，输入和输出是什么，以及每个工作流里隐含了哪些假设。"

Claude Code 读完所有 JSON 文件后返回一个结构化的摘要。这个步骤会揭示一些光看可视化画布看不出来的东西：

→ 哪些工作流共享了对同一凭证的依赖→ 哪些工作流实际上是被父工作流调用的子工作流→ 哪里存在隐含假设（这个字段总是字符串...除了这 12 条记录里它是 null）→ 哪里的错误处理是真的缺失 vs 哪里是 n8n 在静默处理

这个摘要就成了迁移规格说明。我会结合客户上下文来审查它。我标注出需要改变的部分、可以原样重建的部分、以及原始实现就是错的而迁移正好是修复机会的部分。

这个步骤通常花一个下午。但它能省下三天的调试时间。

## 阶段 4：构建迁移（Claude Code 如何做到 n8n 做不到的事）

现在 Claude Code 开始构建实际的系统。

与 n8n 的关键区别：Claude Code 写的是真正的代码。而真正的代码，当你给它正确的文档时，能在故障发生之前就推理出故障模式。

下面这个具体案例让我下定决心投入这次迁移：

在 n8n 里，我们有一个工作流，先调用 Apollo API，然后把线索传给 Apify 爬虫，再把结果发给 Claude 做评分。如果 Apollo 返回 429 限速错误，整个工作流就挂了。下次执行会从头重新处理同样的线索，可能导致重复写入 Airtable。

当我把 Apollo API 文档和 Apify API 文档连同 n8n JSON 一起给 Claude Code 时，它在写一行代码之前就识别出了这个故障模式。它提出了：

→ 针对 Apollo 429 响应的指数退避重试处理器→ 在任何写入操作之前对 Airtable 做线索去重检查→ 一个检查点系统，标记每条线索的处理阶段，这样失败的运行可以从中断处恢复而不是从头开始→ 为 Apify 调用设置异步队列，这样单个爬虫失败不会阻塞其他线索的处理

n8n 无法主动推理出这些。你只能在实际遇到这些故障模式时才发现。而 Claude Code，在给了正确文档的前提下，能在系统投入生产之前就把它们暴露出来。

如何组织构建指令：

按阶段给 Claude Code 下达迁移任务，和任何其他构建一样。

第一阶段：核心数据模型和 API 集成层。 与 Apollo、Apify、Claude、Airtable 通信的函数。每一个都有完善的错误处理、重试逻辑和类型化的输入输出。

第二阶段：编排层。 之前编码在 n8n 可视化流程里的逻辑。哪个函数调用哪个。分支条件是什么。故障如何传播、在哪里被捕获。

第三阶段：前端 dashboard。 这里我使用 21st.dev 的组件库来获取高质量的 React 组件供 Claude Code 引用和实现。用 Google Stitch 快速探索 dashboard 布局，然后再提交完整实现。客户得到一个真正的界面：执行日志、错误报告、手动触发按钮、状态指示器。

第四阶段：后台 worker 和定时任务。 所有按计划运行或响应 webhook 的东西。作为后台服务部署在 Render 上。

## 阶段 5：真正有效的错误处理

这部分值得单独成章，因为它是我们迁移的核心原因。

在 n8n 里，错误处理是结构性的：你给节点添加错误分支，在节点设置中配置重试策略，用 Error Trigger 节点捕获工作流级别的失败。这能用。但它也是可视化的，意味着每个错误处理分支都是在已经很复杂的画布上又多加一个可视节点。

在代码里，错误处理是一等公民。一个 try-catch 可以包裹任何可能失败的操作。一个装饰器处理重试。一个监控钩子在任何未处理异常时触发。逻辑和它保护的函数在同一个文件里，而不是散落在可视化画布的各处。

当我们从 n8n JSON 重建系统时，Claude Code 会做以下事情：

最终的系统是优雅降级而不是灾难性崩溃。如果 Apollo 在限速，队列暂停并重试。如果 Apify 对某条线索返回了格式异常的响应，那条线索被标记，其余的继续处理。如果 Claude 的 API 出现瞬时错误，评分函数会在标记该记录失败之前先进行指数退避重试。

在 n8n 里要全面实现这些，工作流会变得极其复杂。在代码里，这是标准做法。

## 阶段 6：测试重建后的系统

任何重建的系统上线之前，都要经过我们用于所有生产构建的同一套测试框架。

每个核心函数的单元测试。 Apollo enrichment 函数、评分逻辑、Airtable 写入处理器。每一个都用模拟输入进行隔离测试。

使用真实 API 响应的集成测试。 我们把从原始 n8n 执行日志中捕获的 API 响应，回放到新代码上。如果 n8n 工作流正确处理了一批 50 条线索，我们确认重建的系统在相同输入上产出完全一致的输出。

压力测试。 在接入生产之前，我们用 10 倍量级的批次运行重建的系统。如果它能干净地处理 500 条线索，它就能处理 5000 条。

每个 Pull Request 都经过 CodeRabbit 审查。 在人工审查之前先进行自动化代码审查。它能捕捉到我们遗漏的错误处理空白、写得不太对的异步模式、数据处理中的边界情况。

客户验收测试。 客户通过 dashboard 手动触发系统，审查输出结果，在我们从 n8n 切换到重建系统之前签字确认。

切换本身永远不是硬切。我们在第一周并行运行两套系统。n8n 降低运行频率，重建系统按完整频率运行。如果输出一致且新系统的错误率更低，我们就退役 n8n 工作流。

## 客户在迁移前后看到的变化

迁移前： 一个 n8n 的 Loom 录屏讲解。一个他们自己根本看不懂的可视化画布。一个他们无法理解的执行日志。每次出问题都要提交一个支持请求。

迁移后： 一个带着他们 logo 的 dashboard。一张表格展示每次执行、状态和处理了多少条记录。一个日志面板显示最近 10 个错误及人类可读的描述。一个"立即运行"按钮用于手动触发。一个设置面板让他们可以自己更新 ICP 筛选条件，不需要找我们。

系统做的事情完全一样。但拥有它的体验完全不同。

这在商业上很重要。能看到自己系统在运行的客户，对系统更有信心。有信心的客户会续约。而那些依赖 Loom 录屏和支持邮件的客户，离质疑价值永远只差一个糟糕的星期。

Dashboard 不是锦上添花，它是把自动化变成产品的关键。

## 迁移是一条竞争护城河

每家在 n8n 上大规模运行 AI 自动化的 agency 都会撞上我们遇到的同一堵墙。工具确实好用，但到了某个临界点之后就会跟你对着干。

那些想明白如何干净利落地迁移到生产级代码的人，会拥有客户永远不想离开的系统。不是因为锁定效应，而是因为一个定制 dashboard、完善的错误处理、以及能从故障中优雅恢复的系统，本质上就是比一个在大规模下静默崩溃的可视化自动化更好的产品。

我们有 400 个工作流要迁移。我们会在三个月内完成。每完成一个，就把一个客户从脆弱的自动化带向他们真正拥有的系统。

迁移流程：导出 JSON，组织上下文，让 Claude Code 阅读文档并推理故障模式，逐阶段构建，充分测试，通过并行运行完成切换。

就这些。难的不是代码，难的是足够自律地给 Claude Code 提供它一次性做对所需的一切。

核心观点：n8n 在小规模自动化中表现优秀，但在 400+ 工作流的大规模场景下，同步执行、错误不可见、维护困难等问题会成为瓶颈。通过将 n8n 工作流 JSON 导出并交给 Claude Code，可以逐客户、逐阶段地重建为带有完善错误处理、版本控制和客户 dashboard 的生产级代码系统，把"脆弱的自动化"变成"客户真正拥有的产品"。
