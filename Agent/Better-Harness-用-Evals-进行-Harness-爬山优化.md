## Evals 是 Agent 的训练数据

在经典机器学习中，训练数据引导模型的学习过程。每个训练样本贡献一个梯度，将模型的权重更新到"正确"的方向。我们在 agent 领域有类似的学习循环。model + training data + gradient descent → better modelharness + evals + harness engineering → better agentEvals 编码了我们希望 agent 在生产环境中表现出的行为。它们是 harness 工程的"训练数据"。每个 eval 案例贡献一个信号，比如"agent 是否采取了正确的行动"或"是否产生了正确的结果"。这个信号指导对 harness 的下一次修改。我们在模型训练中投入到数据质量和数据策划上的同等严谨和细心，也应该投入到 eval 设计中。我们在之前的文章中讨论了数据质量的重要性，以及我们如何为 Deep Agents 构建 evals。最近有一些很好的工作将优化 harness 的步骤形式化了，包括来自 Stanford 的 Meta-Harness 和来自 DeepMind 的 Auto-Harness。我们之前也分享了一个 Harness 改进循环，仅通过调整 harness 层就在 Terminal Bench 2.0 上实现了爬山优化。我们认为围绕更新算法本身还有很好的未来工作要做，但 harness 改进是一个超越更新算法的复合系统，这也是我们在这里要讨论的内容。Better-Harness 是对复合系统工程的一次尝试。data sourcing → experiment design → optimization → review & acceptance因此，我们包含了与更新循环配套的实践细节，例如我们如何首先获取 evals、如何针对过拟合进行设计、如何随时间存储 Traces，以及如何手动审查更新以对即将投入生产的任何内容进行合理性检查。

## 获取好的 Evals

Evals 是驱动 harness 爬山优化过程的基础。以下是我们获取、策划和使用它们的实践方法。手动策划。对于任何给定任务，团队手动编写示例，捕捉我们认为 agent 在生产中应该做的事情。这些通常价值很高，但难以大规模生成。生产 traces。每次 agent 交互都会生成一个 trace，其中的失败案例会变成 eval 案例。从 traces 中挖掘 eval 素材是一种高杠杆、高吞吐量的方式来随时间改进 evals。甚至在对 evals 运行 agent 之前，通常一个在内部试用我们 agent 的团队就会在 Slack 中直接报告错误并附上 Trace 链接。我们建议内部试用 agent 并直接分享反馈让所有人看到，这有助于建立对 agent 行为的共享认知。外部数据集。这些数据集很有用，但需要手动策划以确保用于改进 agent 的测试用例反映了期望的行为。通常每个任务都会被调整，以确保它们衡量的是重要的行为。标记一切。每个 eval 都被标记到行为类别："tool selection"、"multi-step reasoning"等。标签使有意义的 holdout 集和有针对性的实验成为可能。它还能节省大量成本，因为我们可以运行 evals 的子集。

## 构建能泛化的学习系统

任何学习系统的理想结果都是泛化。我们给出一个输入信号，捕捉我们想要在真实场景中看到的行为分布。系统拟合这个信号，然后在从未见过的新输入上"直接就能工作"。显而易见的问题：我们没有无限的数据。解决方法：将重要行为编码到精心策划的 evals 中。质量 > 数量，一小组涵盖你关心的行为、标记良好的 evals 胜过数千个嘈杂但覆盖面广的 evals。微妙的问题 → agent 是出了名的作弊者：任何学习系统都容易受到 reward hacking 的影响，agent 会过拟合其结构以使它能看到的现有 evals 通过。这是合理的，因为循环只想"让数字上升"，并不了解泛化。我们通过 prompt 来避免过拟合，但这并不完美。解决方法：Holdout 集成为真正泛化的代理指标。我们将其与人工审查配对作为第二信号，这样我们就得到了半自动化系统，可以在提高分数的同时避免我们不想在生产中看到的行为。

## Evals 维护与回归

除了爬山优化之外，evals 还明确地捕捉和防止随时间推移的回归。一旦我们的 agent 正确处理了某个案例，我们就不想失去这个收益。这个 eval 变成了回归测试。这类似于传统软件工程中的想法，比如测试驱动开发（TDD）。随着时间推移的许多更改，一些回归是不可避免的，因此我们选择了一个我们始终希望通过的 evals 子集，如果这些突然失败，我们会对运行结果产生怀疑。我们不认为我们的 eval 套件应该单调递增，定期清理 evals 是好的！我们定期评估一个 eval 是否仍然有用，因为模型变得更智能了，或者我们想要 agent 展现不同的行为。
