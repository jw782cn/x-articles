# [2026-04-09] S3 Files 性能深度分析

好，是时候做一些区分了。我一直跟大家解释，EFS（S3 Files）没有发挥出全部潜力，原因有三个：性能、价格，以及和 S3 在主存储上存在一种奇怪的竞争关系。

AWS 已经把和 S3 的竞争问题解决了（这很棒），但今天我们来聊聊性能。

EFS 如今已经是一门大生意了，但它还没有 AWS 最大的 SSD 业务那么大——也就是 Elastic Block Store（EBS）。

EBS 就是你启动一台 EC2 主机时获得的磁盘。它允许你把磁盘从一台主机上分离出来（即使实例被终止也能保留数据），允许你扩大磁盘容量（但不能缩小），并且提供一个持久化的设备，让你可以在上面运行常规软件而不用担心数据丢失。

因此，大多数数据库产品（直到 @samlambert 开始推动 Metal 之前），包括 PlanetScale（非 Metal 版本）、Supabase、RDS（非 Aurora 版本），以及其他一些 AWS 文件产品，本质上就是在 EBS 卷上运行数据库和文件系统软件的封装。还有很多基础设施公司正在构建自己的"基于 S3 的 EBS"来扩展这个基础能力。

那为什么 AWS 里不是所有软件都用 EBS 呢？答案是：可用性和可扩展性。

EBS 磁盘就像你笔记本电脑上的硬盘一样，它们内部没有任何逻辑来允许多台机器在同一组数据上进行协调。

这意味着，如果你想实现真正的零停机部署，你就不能把数据放在 EBS 卷上，因为当挂载它的那台（唯一的）实例需要重启时，数据将不可用。

通常，这就是我们看到人们开始迁移到像 EFS 这样的文件系统产品的原因。文件系统是智能的，你告诉它你正在创建和使用哪些文件，它可以利用这些信息让多个客户端安全地连接到同一数据集。因此，当人们需要以下两点时，就会从 EBS 迁移到 EFS：（a）将现有应用水平扩展到多台机器，或者（b）增加高可用性。

问题来了——当有人迁移到 EFS 后，他们的应用就会爆炸。不是字面意义上的爆炸，而是性能会变得非常糟糕。

这是文件系统和块存储在工作方式上的一个根本性差异。当你在笔记本电脑上，或者在 AWS 中使用 NVMe 或 EBS 卷"创建一个文件"时，没有任何数据被写入磁盘。内核只是在内存中记下这个操作，直到应用程序通过 fsync 请求磁盘写入。

当你使用像 EFS（或任何基于 NFS 的文件系统）这样的文件系统时，情况就不同了。如果用户 A 和用户 B 都连接到同一个磁盘，并且都想创建"hello.txt"，那么唯一能决定哪个用户可以创建这个文件的地方就是服务器。

因此，NFS 中的元数据操作在每一个修改操作上都需要往返服务器。这使得它对很多类型的应用来说不可用，也意味着尽管 EFS/S3 Files 团队雇用了大量优秀的工程师在努力降低单次操作的延迟，但对于大多数交互式工作负载来说，它始终会比 EBS 慢一个数量级。

我认为这是一个糟糕的状况。文件存储比块存储能提供多得多的能力：按使用量计费、在语义层面理解用户意图、提供离线访问。我们没有理由必须接受文件存储就是比普通块存储慢这么多的现实。

在 Archil，我们没有接受这个现实。我们通过构建自己的协议（替代 NFS）来解决这个问题，这个协议借鉴了 Andrew File System（AFS）的设计思想。我们的协议允许客户端对文件系统的不同部分进行"签出"和"签入"操作，以表明他们需要对这部分数据的独占写入权限。

当一个客户端拥有文件系统某部分的独占写入权限时，它就能使用和 EBS 或 NVMe 上的文件系统相同的持久化语义（除非被要求，否则不写入磁盘），从而弥合性能差距。

实际效果是，我们在几乎没有花时间做性能优化的情况下，就实现了相对于 EFS/S3 Files 的显著速度提升。

这也是为什么我们能够招到曾经在这个产品上工作的人。超越 S3 Files（EFS）从来不是我们的终极目标，成为用户在云端存储数据的默认方式才是。而要做到这一点，你必须取代 EBS。

核心观点：EFS/S3 Files 因 NFS 协议的固有限制（每次元数据操作都需往返服务器），在性能上始终比 EBS 慢一个数量级。Archil 通过借鉴 AFS 设计构建自有协议，引入"签出/签入"机制实现独占写入，在几乎不做性能优化的情况下大幅超越 EFS，其终极目标不是超越 EFS，而是取代 EBS 成为云端数据存储的默认方式。
