# [2026-04-13] 为什么你的AI-First策略可能是错的

**原文链接**：[Why Your "AI-First" Strategy Is Probably Wrong](https://x.com/intuitiveml/status/2043545596699750791) by **@intuitiveml****67万阅读** | **1540点赞** | **4959收藏**

我们 99% 的生产代码都由 AI 编写。上周二，我们早上 10 点上线了一个新功能，中午做完 A/B 测试，下午 3 点因为数据表现不佳而下掉了它。下午 5 点，我们上线了一个更好的版本。三个月前，这样一个循环需要六周时间。

我们并不是靠在 IDE 里加个 Copilot 做到的。我们拆掉了整个工程流程，围绕 AI 重新构建。我们改变了规划、构建、测试、部署的方式，改变了团队的组织方式，改变了公司里每个人的角色。

CREAO 是一个 Agent 平台。25 名员工，10 名工程师。我们从 2025 年 11 月开始构建 Agent，两个月前我从零开始重构了整个产品架构和工程工作流。

OpenAI 在 2026 年 2 月发表了一个概念，恰好描述了我们一直在做的事情。他们称之为 harness engineering：工程团队的首要工作不再是写代码，而是让 Agent 能够完成有用的工作。当某件事失败时，解决方案永远不是「再努力一点」，而是：缺少了什么能力？我们如何让它对 Agent 来说是可感知且可执行的？

我们自己独立得出了同样的结论。只是当时我们没给它起名字。

## AI-First 不等于使用 AI

大多数公司只是把 AI 贴到了现有流程上。工程师打开 Cursor，PM 用 ChatGPT 起草需求文档，QA 尝试用 AI 生成测试。工作流没变，效率提升了 10% 到 20%，但结构性上什么都没有改变。

这叫 AI-assisted（AI 辅助）。

AI-first 意味着你围绕「AI 是主要构建者」这个假设，重新设计你的流程、架构和组织。你不再问「AI 怎么帮助我们的工程师？」，而是开始问「我们如何重构一切，让 AI 来构建，让工程师提供方向和判断？」

两者的差距是乘数级的。

我看到有些团队号称 AI-first，但还在跑同样的 sprint 周期、同样的 Jira 看板、同样的每周站会、同样的 QA 签字流程。他们只是在循环中加入了 AI，而没有重新设计这个循环。

一种常见的做法是人们所说的 vibe coding。打开 Cursor，不停 prompt 直到能跑通，提交代码，重复。这能产出原型。但生产系统需要稳定、可靠、安全。你需要一个在 AI 写代码时能保证这些属性的系统。你构建的是系统，prompt 是一次性的。

## 为什么我们必须改变

去年，我观察了团队的工作方式，发现了三个会让我们死掉的瓶颈。

**产品管理瓶颈**

我们的 PM 花好几周时间做调研、设计、撰写功能规格。产品管理几十年来一直是这样运作的。但 Agent 可以在两小时内实现一个功能。当构建时间从几个月缩短到几小时，几周的规划周期就成了瓶颈。

花几个月思考一个东西，然后两小时就能建好，这说不通。

PM 需要进化成具有产品思维的架构师，跟上迭代速度，否则就得退出构建循环。设计需要通过「快速原型-上线-测试-迭代」的循环来完成，而不是在委员会里评审规格文档。

**QA 瓶颈**

同样的问题。Agent 上线一个功能后，我们的 QA 团队花好几天测试边界情况。构建时间：两小时。测试时间：三天。

我们用 AI 构建的测试平台取代了手动 QA，让 AI 测试 AI 写的代码。验证必须和实现保持同样的速度，否则你只是把瓶颈从上游移到了下游十英尺远的地方。

**人员瓶颈**

我们的竞争对手有 100 倍甚至更多的人在做类似的工作。我们只有 25 人。我们不可能靠招人追上他们，必须靠重新设计来实现。

三个系统需要 AI 贯穿其中：我们如何设计产品、如何实现产品、如何测试产品。任何一个环节保持手动，都会拖住整条流水线。

## 大胆的决定：统一架构

我得先修好代码库。

我们的旧架构分散在多个独立系统中。一个改动可能需要动三四个代码仓库。对人类工程师来说，这还能应付。但对 AI Agent 来说，完全不透明。Agent 看不到全貌，无法推理跨服务的影响，无法在本地运行集成测试。

我必须把所有代码统一到一个 monorepo 中。一个原因：让 AI 能看到一切。

这就是 harness engineering 原则的实践。你把系统的越多部分拉到 Agent 可以检查、验证和修改的形式中，你获得的杠杆就越大。碎片化的代码库对 Agent 来说是不可见的，统一的代码库是可读的。

我花了一周时间设计新系统：规划阶段、实现阶段、测试阶段、集成测试阶段。然后又花了一周时间用 Agent 重构整个代码库。

CREAO 是一个 Agent 平台。我们用自己的 Agent 来重建运行 Agent 的平台。如果产品能构建自身，那它就能用。

## 技术栈

以下是我们的技术栈以及每个部分的作用。

**基础设施：AWS**

我们运行在 AWS 上，使用自动伸缩的容器服务和熔断回滚机制。如果部署后指标恶化，系统会自动回滚。

CloudWatch 是中枢神经系统。所有服务的结构化日志，超过 25 个告警，自定义指标由自动化工作流每天查询。每一块基础设施都暴露结构化的、可查询的信号。如果 AI 读不了日志，它就无法诊断问题。

**CI/CD：GitHub Actions**

每次代码变更都经过六阶段流水线：

验证 CI → 构建部署 Dev → 测试 Dev → 部署 Prod → 测试 Prod → 发布

每个 Pull Request 上的 CI 门禁强制执行类型检查、代码规范、单元测试和集成测试、Docker 构建、Playwright 端到端测试和环境一致性检查。没有可选阶段，没有手动覆盖。流水线是确定性的，所以 Agent 可以预测结果并推理故障。

**AI 代码审查：Claude**

每个 Pull Request 会触发三轮并行的 AI 审查，使用 Claude Opus 4.6：

第一轮：代码质量。逻辑错误、性能问题、可维护性。

第二轮：安全性。漏洞扫描、认证边界检查、注入风险。

第三轮：依赖扫描。供应链风险、版本冲突、许可证问题。

这些是审查门禁，不是建议。它们与人工审查并行运行，在高频部署中捕捉人类遗漏的问题。当你一天部署八次，没有人类审查者能在每个 PR 上保持注意力。

工程师还可以在任何 GitHub Issue 或 PR 中 @claude，获取实现方案、调试会话或代码分析。Agent 能看到整个 monorepo，上下文在对话间延续。

**自愈反馈循环**

这是核心。

每天早上 UTC 时间 9:00，一个自动化健康工作流运行。Claude Sonnet 4.6 查询 CloudWatch，分析所有服务的错误模式，并生成一份执行层面的健康摘要，通过 Microsoft Teams 推送给团队。不需要任何人主动去要。

一小时后，分诊引擎启动。它聚类来自 CloudWatch 和 Sentry 的生产错误，在九个严重性维度上对每个聚类评分，并自动在 Linear 中生成调查工单。每个工单包含样本日志、受影响用户、受影响端点和建议的调查路径。

系统会去重。如果已有未关闭的 Issue 覆盖了相同的错误模式，就更新该 Issue。如果之前关闭的 Issue 再次出现，系统会检测到回归并重新打开。

当工程师推送修复后，同一条流水线处理。三轮 Claude 审查评估 PR，CI 验证，六阶段部署流水线在 Dev 和 Prod 环境间逐级推进并在每个阶段测试。部署后，分诊引擎重新检查 CloudWatch。如果原始错误已解决，Linear 工单自动关闭。

每个工具处理一个阶段，没有工具试图做所有事情。每日循环创造了一个自愈闭环，错误被检测、分诊、修复和验证，几乎不需要人工干预。

我对 Business Insider 的记者说过：「AI 会创建 PR，人类只需要审查是否有风险。」

**Feature Flags 和配套工具栈**

Statsig 管理 Feature Flags。每个功能都在门禁后面上线。上线模式：先对团队开放，然后逐步按百分比放量，最后全量发布或下掉。Kill switch 可以即时关闭一个功能，无需部署。如果某个功能导致指标下降，我们在几小时内就会撤掉它。坏功能在上线当天就会被干掉。A/B 测试通过同一套系统运行。

Graphite 管理 PR 分支：合并队列 rebase 到 main 上，重跑 CI，只有绿色才合并。Stacked PR 允许在高吞吐量下进行增量审查。

Sentry 报告所有服务的结构化异常，由分诊引擎与 CloudWatch 合并以获取跨工具上下文。Linear 是面向人类的层：自动创建的工单带有严重性评分、样本日志和建议调查方向。去重防止噪音。后续验证自动关闭已解决的问题。

## 成果

在 14 天内，我们平均每天进行 3 到 8 次生产部署。在旧模式下，整个两周时间甚至连一次生产发布都完成不了。

坏功能在上线当天就被撤掉。新功能在构思当天就能上线。A/B 测试实时验证效果。

人们以为我们是在用质量换速度。实际上用户参与度上升了，付费转化率上升了。我们产出了比以前更好的结果，因为反馈循环更紧密了。每天发版比每月发版能学到更多东西。

## 新型工程组织

未来会存在两类工程师。

**架构师**

一到两个人。他们设计标准操作流程（SOP），教 AI 如何工作。他们构建测试基础设施、集成系统、分诊系统。他们决定架构和系统边界，他们定义对 Agent 来说什么是「好」。

这个角色需要深度的批判性思维。你批评 AI，而不是跟随它。当 Agent 提出方案时，架构师找出漏洞：它漏掉了哪些故障模式？越过了哪些安全边界？在积累什么技术债？

我有物理学博士学位。博士训练教给我的最有用的东西，是如何质疑假设、压力测试论点、寻找遗漏。批评 AI 的能力将比编写代码的能力更有价值。

这也是最难招到人的角色。

**操作员**

其他所有人。工作同样重要，但结构不同。

AI 给人类分配任务。分诊系统发现一个 Bug，创建工单，呈现诊断结果，分配给合适的人。这个人调查、验证并审批修复。AI 创建 PR，人类审查是否有风险。

任务包括 Bug 调查、UI 优化、CSS 改进、PR 审查和验证。这些需要技能和注意力，但不需要旧模式所要求的架构推理能力。

**谁适应得最快**

我注意到了一个出乎意料的模式。初级工程师比高级工程师适应得更快。

传统经验较少的初级工程师感到被赋能了。他们获得了放大自身影响力的工具，不需要卸载十年的习惯。

传统实践经验丰富的高级工程师反而最难适应。他们两个月的工作量，AI 一小时就能完成。在花了多年构建稀缺技能后，这很难接受。

我不做评判，只是描述我观察到的。在这个转型中，适应力比积累的技能更重要。

## 人的一面

**管理坍缩了**

两个月前，我 60% 的时间花在管理人上。对齐优先级、开会、给反馈、辅导工程师。

现在：不到 10%。

传统 CTO 模式说要赋能团队去做架构工作，培养他们，委派任务。但如果系统只需要一两个架构师，我得先自己上。我从管理转向了构建。大多数日子我从早上 9 点写代码到凌晨 3 点。我设计系统的 SOP 和架构，我维护 harness。

压力更大了。但我享受构建，而不是对齐。

**更少争论，更好关系**

我和联合创始人、工程师的关系比以前更好了。

转型之前，我和团队的大部分互动都是对齐会议。讨论权衡、辩论优先级、在技术决策上产生分歧。这些对话在传统模式中是必要的，但也很消耗人。

现在我仍然和团队交流，但我们聊别的事。非工作话题、闲聊、团建旅行。我们相处得更好了，因为我们不再为那些系统能轻松搞定的工作争论了。

**不确定性是真实的**

我不会假装所有人都开心。

当我不再每天和人交流时，一些团队成员感到不安。CTO 不和我说话了是什么意思？在这个新世界里我的价值是什么？这些是合理的顾虑。

有些人花在讨论「AI 能不能做他们的工作」上的时间，比做工作本身还多。转型期会制造焦虑。我没有一个干净利落的答案。

但我有一个原则：我们不会因为一个工程师引入了生产 Bug 就开除他。我们改进审查流程，加强测试，增加护栏。对 AI 也是一样。如果 AI 犯了错，我们构建更好的验证、更清晰的约束、更强的可观测性。

## 超越工程

我看到其他公司采用了 AI-first 工程，但其他一切仍然是手动的。

如果工程在几小时内上线功能，但市场部门要一周才能发布公告，那市场就是瓶颈。如果产品团队还在跑月度规划周期，规划就是瓶颈。

在 CREAO，我们把 AI-native 运营推进到了每一个职能：

工程、产品、市场和增长在一个 AI-native 工作流中运行。如果一个职能以 Agent 速度运行，而另一个以人类速度运行，人类速度的职能就会拖住一切。

## 这意味着什么

**对工程师**

你的价值正在从代码产出转向决策质量。快速写代码的能力每个月都在贬值，评估、批评和指导 AI 的能力每个月都在增值。

产品感觉（taste）很重要。你能在用户告诉你之前，看出一个生成的 UI 是错的吗？你能看出 Agent 提出的架构方案中遗漏的故障模式吗？

我告诉我们 19 岁的实习生：训练批判性思维。学会评估论点、发现漏洞、质疑假设。学会什么是好的设计。这些技能会复利增长。

**对 CTO 和创始人**

如果你的 PM 流程比构建时间还长，从那里开始改。

在扩展 Agent 之前先建好测试 harness。没有快速验证的快速 AI，只是快速产生的技术债。

从一个架构师开始。一个人来构建系统并证明它可行。在系统运行后，再把其他人纳入操作员角色。

把 AI-native 推进到每个职能。

预期会有阻力。有些人会反对。

**对整个行业**

OpenAI、Anthropic 和多个独立团队在相同原则上达成了共识：结构化上下文、专业化 Agent、持久化记忆和执行循环。Harness engineering 正在成为标准。

模型能力是驱动这一切的时钟。我把 CREAO 的整个转变归因于最近两个月。Opus 4.5 做不到 Opus 4.6 能做的事。下一代模型会进一步加速。

我相信一人公司将变得普遍。如果一个架构师加上 Agent 能做 100 个人的工作，很多公司不需要第二个员工。

## 我们还很早期

我交流过的大多数创始人和工程师仍然在用传统方式运作。有些人在思考转型，真正做了的寥寥无几。

一位记者朋友告诉我，她在这个话题上大约采访了五个人。她说我们比任何人都走得更远：「我觉得没有人像你们这样彻底重建了整个工作流。」

任何团队都有条件做到这些。我们技术栈中没有任何东西是私有的。

竞争优势在于围绕这些工具重新设计一切的决定，以及愿意承受这个代价。代价是真实的：员工的不确定感、CTO 每天工作 18 小时、高级工程师质疑自己的价值、两周时间里旧系统已经不在了而新系统还没有被证明。

我们承受了这些代价。两个月后，数据说明一切。

我们构建 Agent 平台。我们用 Agent 构建了它。

**核心观点**：AI-first 不是在现有流程上加 AI 工具，而是围绕「AI 是主要构建者」这一假设彻底重构流程、架构和组织。真正的竞争优势不在于工具本身，而在于敢于承受转型代价、彻底重建一切的决心。
