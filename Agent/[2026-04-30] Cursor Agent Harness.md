# [2026-04-30] Cursor Agent Harness

我们构建 Cursor agent harness 的方式，和我们做任何有野心的软件产品一样。大量工作是愿景驱动的——我们先形成对理想 agent 体验应该是什么样的看法。

在此基础上，我们提出假设来靠近这个愿景，通过实验来验证假设，然后利用 eval 和真实使用中的定量与定性信号不断迭代。这个过程依赖于正确的线上和线下监测体系，让我们能够判断某个改动是否真的让 harness 变得更好。

当我们提前拿到新模型的使用权限时，所有这些方法会汇聚在一起。我们会花数周时间针对一个模型的优势和特性来定制我们的 harness，直到同一个模型在我们精心调优的 harness 中明显变得更快、更聪明、更高效。

偶尔我们会发现阶跃式的提升。但更多时候，改进 harness 是一件需要执着地叠加小优化的事情，这些小优化加在一起，让 agent 更擅长构建软件。

## 进化中的 Context Window

与大语言模型交互的核心是 context window。当你让 agent 去构建某个东西时，context window 从 system prompt 和 tool 描述开始，接着是当前对话的状态，最后是用户的请求。

我们填充和管理这个窗口的方式，在 Cursor 的历史中经历了巨大的演变。

当我们在 2024 年底首次开发编码 agent 时，模型在自主选择上下文方面还很差，我们在 context engineering 上投入了大量工作来创建护栏——例如，在每次编辑后将 lint 和类型错误展示给 agent，当它请求的行数太少时重写它的文件读取，甚至限制它在一个回合中能调用的最大 tool 数量。

我们还在每个会话开始时提供了大量静态上下文，始终对 agent 可用。在不同阶段，这些上下文包括代码库的文件夹结构、与查询语义匹配的代码片段，以及用户手动附加的文件的压缩版本。

这些基本上已经成为过去。

我们仍然保留了一些有用的静态上下文（例如操作系统、git 状态、当前和最近查看的文件）。但我们通过拆除护栏并提供更多动态上下文来适应不断增强的模型能力，这些动态上下文可以在 agent 工作时由它自己获取。在之前的一篇文章中，我们深入探讨了一些动态上下文背后的技术，其中许多后来被其他编码 agent 采用。我们现在的工作重点是为 agent 提供更多动态获取上下文和与外部世界交互的方式。

## 评估 Harness 变更的两种方式

Harness 和模型共同决定了 agent 有多好，但"好"很难精确定义。为了定位它，我们构建了多层度量体系。

我们维护着公开的 benchmark，同时还有我们自己的 eval 套件 CursorBench，它为我们提供了快速、标准化的质量评估，并允许我们进行跨时间的对比。但即使是最好的 benchmark 也只是近似真实使用，如果完全依赖它们，我们会错过重要的信号。

因此，我们还进行线上实验，将两个或更多 harness 变体并行部署，在真实使用中进行 A/B test。我们通过多种指标来衡量这些测试中的 agent 质量。一些指标很直接，比如延迟、token 效率、tool call 次数和 cache 命中率。这些在方向上是有用的，但仍然无法触及更模糊但更重要的问题——agent 是否真的做好了它的工作。我们通过两种方式来衡量这一点。

第一种是 agent 生成代码的 Keep Rate。对于 agent 提出的一组代码变更，我们追踪在固定时间间隔后，这些变更中有多少比例仍然保留在用户的代码库中。这让我们能够了解用户何时需要手动调整 agent 的输出，或者需要迭代让 agent 修复问题，这表明 agent 的初始响应质量较低。

第二种是使用语言模型来阅读用户对 agent 初始输出的回应，从语义上捕捉用户是否满意。用户转而处理下一个功能是 agent 完成工作的强信号，而用户粘贴一个 stack trace 则是 agent 没有完成工作的可靠信号。

有时候这些线上测试会告诉我们搁置一个看起来很有前景的想法。在一次实验中，我们尝试用一个更昂贵的模型来做上下文摘要，结果发现它对 agent 质量的提升微乎其微，不值得付出更高的成本。

## 追踪和修复退化

随着我们添加更多模型和能力，harness 变得越来越复杂，有更多的潜在状态，就像任何软件一样。随之而来的是更大的 bug 出现面，其中许多只有在大规模运行时才能被检测到。

Agent 的 tool 是 bug 出现面最广的区域之一，而 tool call 错误对 Cursor 中的一个会话可能造成极大的伤害。虽然 agent 通常可以自我纠正，但错误会留在上下文中，浪费 token 并导致"context rot"——累积的错误会降低模型后续决策的质量。

有时候，agent 会在一次失败的 tool call 后被阻塞或完全跑偏。虽然 tool call 调用量和错误率等指标并不直接衡量 agent 是否做好了工作，但它们可以作为指向更深层问题的指示器。

任何未知错误都代表着 harness 中的一个 bug，我们也会这样处理它。但许多错误是"预期内的"，例如模型偶尔提出一个不正确的编辑，或者尝试读取一个不存在的文件。我们按原因对这些预期错误进行分类。InvalidArguments 和 UnexpectedEnvironment 捕获模型的错误和 context window 中的矛盾，而 ProviderError 捕获来自 GenerateImage 或 WebSearch 等 tool 的供应商故障。

我们还有其他几种分类，比如 UserAborted 和 Timeout，它们加在一起涵盖了大部分预期错误。

我们基于这些指标定义告警，以捕获进入生产环境的重大退化。由于未知错误始终是 bug，当任何 tool 的未知错误率超过固定阈值时我们就会告警。但要判断预期错误是 harness 中的 bug 还是预期行为，可能很棘手。

例如，grep 搜索超时可能是因为 tool 的性能问题，也可能是因为代码库确实很大而模型构造了一个低效的查询。为了应对这种情况，我们设置了异常检测告警，当预期错误显著超过基线时就会触发。我们按 tool 和模型分别计算基线，因为不同的模型可能以不同的频率搞砸 tool call。

我们还运行一个每周自动化流程，它配备了一个 skill，教模型如何搜索我们的日志、找出新出现或近期激增的问题，并在待办列表中创建或更新工单进行调查。我们大量依赖 Cloud Agent 来同时启动多个问题的修复，甚至可以直接从 Linear 触发它们。

这个流程是我们为 agent harness 构建自动化"软件工厂"的一部分。在今年早些时候一次集中冲刺中，我们将意外的 tool call 错误降低了一个数量级。

## 为不同模型定制 Harness

我们所有的 harness 抽象都是模型无关的，可以为我们支持的每个模型进行深度定制。例如，OpenAI 的模型被训练使用基于 patch 的格式来编辑文件，而 Anthropic 的模型则被训练使用字符串替换。任何一个模型都可以使用另一种 tool，但给它不熟悉的那种会消耗额外的推理 token 并产生更多错误。所以在我们的 harness 中，我们为每个模型配置它在训练时使用的 tool 格式。

这种定制非常深入，包括为不同提供商甚至不同模型版本进行自定义的 prompting。OpenAI 的模型在指令遵循上更为字面和精确，而 Claude 则更为直觉化，对不精确的指令有更高的容忍度。

当我们在发布前提前拿到一个新模型时，我们从最接近的现有模型的 harness 开始迭代。我们运行离线 eval 来找出模型在哪里犯迷糊，让团队成员使用它并反馈问题，然后相应地调整 harness。我们就这样迭代，直到我们对一个模型-harness 组合有信心可以交付。

这个调优过程大部分是关于让 harness 适应新模型的优势，但有时我们会遇到真正的模型怪癖，可以通过 harness 来缓解。例如，我们观察到一个模型产生了我们后来称之为 context anxiety 的现象：随着 context window 被填满，它开始拒绝工作，辩解说任务似乎太大了。我们通过 prompt 调整成功减少了这种行为。

### 支持对话中途切换模型

设计 harness 来支持用户在对话中途切换模型尤其棘手，因为不同的模型有不同的行为、prompt 和 tool 形态。

当用户切换模型时，Cursor 会自动切换到相应的 harness，使用该模型定制的 prompt 和 tool 集。然而，模型仍然需要将这些 tool 应用到一段由不同模型产生的对话历史上，而这段历史与它训练时的数据分布不同。

为了解决这个问题，我们添加了自定义指令，告诉模型它正在从另一个模型那里接管对话。这些指令还会引导它避免调用那些出现在对话历史中但不属于它自己 tool 集的 tool。

第二个挑战是 cache 是按提供商和模型分隔的，所以切换意味着 cache miss 和更慢、更昂贵的第一次回复。我们通过在切换时总结对话来缓解这个问题，为模型提供一个干净的摘要来减少 cache 惩罚。但如果用户正在进行一个复杂的任务，摘要可能会丢失重要细节，这也是为什么我们通常建议在整个对话过程中使用同一个模型，除非你有切换的理由。

另一种绕过对话中途模型切换挑战的方法是改用 subagent，它从一个全新的 context window 开始。我们最近在 harness 中添加了让用户直接要求使用特定模型运行 subagent 的能力。

## Harness 与软件开发的未来

AI 辅助软件工程的未来将是多 agent 的。系统不再通过单一 agent 处理每个子任务，而是学会在专业化的 agent 和 subagent 之间进行委派：一个负责规划，一个负责快速编辑，第三个负责调试，每个都专注于它最擅长的领域。

让这一切运转良好，从根本上说是一个 harness 挑战。系统需要知道该调度哪个 agent，如何为该 agent 的优势来组织任务，以及如何将结果拼接成连贯的工作流。编排这种协调的能力将存在于 harness 中，而非任何单一 agent。这意味着，虽然 harness 工程一直对 agent 的成功很重要，但它在未来只会变得更加关键。

**核心观点**：Agent 的能力不仅取决于模型本身，更取决于 harness 的工程质量。Cursor 团队通过愿景驱动的迭代、多层度量体系（Keep Rate、线上 A/B test、异常检测）、针对每个模型的深度定制，以及自动化的退化追踪和修复流程，持续将 harness 的小优化叠加成显著的体验提升。未来的多 agent 架构将使 harness 工程变得比以往任何时候都更加关键。
