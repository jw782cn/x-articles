你用 AI 用得不好，不是因为你没找到正确的模型。

你用 AI 用得不好，是因为你没有构建正确的环境。

有些团队三个工程师就能交付百万行代码，而有些团队连一次一致的重构都搞不定。差异不在于 GPT-5 和 Claude Opus 的区别，不在于温度设置或最大 token 数，甚至不在于提示词——尽管每个人都在提示词上浪费了大量时间。

差异在于 Harness（运行环境框架）。

本文将深入讲解这个词的技术和哲学含义。Harness 不是系统提示词，不是 API 调用的封装器，不是评估框架或提示词模板或带记忆的聊天机器人。Harness 是语言模型运行的完整设计环境，包括它能调用的工具、接收信息的格式、历史记录的压缩和管理方式、防止错误级联的护栏，以及允许它将工作交接给未来自己而不丧失连贯性的脚手架。

当你审视 Anthropic 为让 Claude Code 真正工作所做的事情、OpenAI 为通过 Codex 零人工代码交付百万行代码所做的事情，以及普林斯顿 NLP 团队在其里程碑式的 SWE-agent 论文中关于 Agent-计算机接口的研究时，你会看到每个认真研究这个领域的团队都浮现出相同的模式。

模型几乎无关紧要。Harness 才是一切。

这是一篇详细的技术拆解，讲述这个洞察如何在 2025 和 2026 年成为应用 AI 工程的核心见解。它涵盖了研究、真实的实现、驱动设计决策的失败模式，以及无论你构建编码 Agent、研究 Agent 还是长时间运行的自主软件工程师时都会重复出现的模式。

# 第一部分：没人谈论的问题

## 为什么原始能力远远不够

2024 年中期，AI 基准测试出现了一件奇怪的事。研究人员开始注意到，同一个前沿模型在完全相同的编码任务上可能产生截然不同的结果，而唯一的区别仅仅是任务的呈现方式和可用的工具。模型没变，底层智能没变。变的是接口。

这本不该令人惊讶。我们早就知道合适的工具能让工程师的生产力大幅提升。一个拥有现代 IDE、调试器、版本控制和 CI/CD 流水线的软件开发者，比同一个只用文本编辑器在终端里工作的开发者高效数个数量级。IDE 不会让开发者更聪明，它消除了摩擦、在合适的时机呈现信息、提前捕获错误、将工作组织为可导航的单元。

语言模型也是一样。它们不是从无限内部知识库中工作的通用推理器。它们是在上下文窗口中对 token 进行操作的复杂模式匹配引擎。它们在某一时刻知道的一切由上下文窗口中的内容决定，它们产出的一切由上下文的结构方式所影响。输入的格式不是装饰，它是 Agent 的认知架构。

接口不是便利层。对于 LM Agent 来说，接口就是思维本身。

这是普林斯顿 NLP 团队在 2024 年发表的 SWE-agent 论文的核心主张，经得起检验。该论文引入了 Agent-计算机接口（ACI）的概念，证明精心设计的 ACI 能比同一模型通过标准 Linux shell 交互时，在基准性能上提升 64%。同一模型，同一任务，同一计算预算。唯一的变量是接口。

停下来想想：64% 不是微小的提升。这是工具能用和不能用的区别。而且完全来自环境设计，不是底层模型的任何改进。

## 上下文窗口不是内存插槽

对 AI Agent 的天真心智模型把上下文窗口当 RAM 用：你把数据加载进去，模型处理它，你得到输出。更多上下文等于更好的性能。更长的提示词等于更丰富的理解。这个心智模型是错的，而且错得会毁掉你的 Agent。

上下文窗口实际上更接近于 Agent 在给定会话中的全部工作意识。窗口中的每个 token 都消耗计算资源。每一条不相关的信息都在与相关信息竞争注意力。模型没有能干净地忽略噪音的选择性注意力机制——噪音就在房间里，它会影响推理。

这带来了具体的、可衡量的后果。当你在 Agent 循环中对大型代码库运行 grep 并返回一万行匹配结果时，你并没有给 Agent 更多信息。你淹没了它的工作记忆，直到上下文被清除前，后续每一步的质量都会下降。当你用 cat 转储整个文件而 Agent 只想看两个函数时，你给了它一个消防水管而它只需要一杯水。

SWE-agent 的研究者们细致地记录了这些失败模式。标准 bash 接口导致 Agent 陷入混乱。它们会发出 grep 命令返回数千行，迷失方向，再发更多 grep 命令，逐渐用噪音填满上下文，最终要么给出错误答案，要么完全停止进展。问题不在于模型智能，问题在于接口没有保护 Agent 免受自身伤害的机制。

ACI 的解决方案是构建一个搜索工具，返回有上限的、摘要化的结果列表。如果你的搜索返回超过 50 条匹配，工具会抑制输出并告诉 Agent 缩小查询范围。这个设计决策回过头来看几乎简单到令人发指，却是整篇论文中杠杆效应最高的变更之一。它将上下文溢出的失败模式转变为自然的细化循环。

# 第二部分：SWE-Agent 论文与 ACI 的诞生

## Agent-计算机接口到底是什么

ACI 在 SWE-agent 论文中被定义为位于语言模型 Agent 和计算机环境之间的抽象层。与人机接口（HCI）的类比是有意为之的。正如 HCI 研究探讨如何设计匹配人类认知架构的接口，ACI 研究探讨如何设计匹配 LM 认知架构的接口。

人类认知架构涉及视觉模式识别、空间记忆、屏幕上的并行注意力以及浏览和选择性聚焦的能力。LM 认知架构根本不同：它涉及顺序 token 处理、对上下文顺序和格式的敏感性、有限的工作记忆，以及锚定在提示词中最突出信息上的倾向。设计好的 ACI 意味着理解这些约束并围绕它们构建，而不是与之对抗。

SWE-agent 用于编码任务的 ACI 有四个主要组件，每一个都反映了关于语言模型在获得原始计算机访问权限时如何失败的具体洞察。

搜索与导航

搜索组件用专门构建的工具替代了标准的 grep 和 find 命令：find_file、search_file 和 search_dir。关键区别不在于语法，而在于输出管理。结果上限为 50 条。如果查询超过限制，工具会返回消息说明结果太多并提示 Agent 细化搜索。这听起来微不足道，实际上却是论文中最具影响力的决策之一。

原因在于 Agent 和认知负荷下的人类一样，在感到不确定时倾向于继续做正在做的事。当人在大型代码库中迷失时，他们会搜索得越来越广，产生越来越多的噪音。有上限的搜索工具通过创建强制函数来打断这种模式。你不能靠模糊继续下去，你必须精确。这推动 Agent 走向更审慎、更有针对性的行为。

文件查看器

文件查看器是论文关于认知架构的洞察最具体的地方。研究人员测试了多种查看器配置，发现每次显示 100 行是一个恰到好处的数字。更少的行（他们测试了 30 行）导致 Agent 失去周围代码的上下文并犯编辑错误。更多的行（或完整文件）导致 Agent 迷失位置并遗漏重要细节。

查看器是有状态的。它在交互间维护文件中的位置。关键的是，它在每一行可见行前添加了明确的行号。这个细节看起来是装饰性的，其实不是。当 Agent 需要发出针对第 47 到 52 行的编辑命令时，它需要能够直接从视图中读取这些数字，而不是计数或做算术。将这个认知任务从 Agent 的工作记忆中移除，为实际的问题解决腾出了空间。

带 Linting 的文件编辑器

文件编辑器的关键创新是即时反馈加护栏。编辑命令接受起始行、结束行和替换文本作为单一操作。每次编辑后，工具自动对修改后的文件运行 linter 并报告结果。如果编辑引入了语法错误，编辑在应用前就被拒绝，Agent 会收到清晰的错误消息，显示原始代码和失败的编辑。

这关闭了导致天真 Agent 实现中级联失败的反馈循环。没有 linter，Agent 可能引入语法错误，运行测试套件，看到一个似乎不相关的失败，花多个步骤追踪错误问题，最终在追逐幽灵中耗尽上下文窗口。将 linter 直接集成到编辑器中，语法错误在引入时就被捕获，修复在问题传播之前就本地化了。

上下文管理

第四个组件解决了一个在长会话中不断积累的问题：陈旧上下文的累积。随着 Agent 处理任务，它的历史记录会充满旧的观察、中间状态和不再反映当前环境状态的探索性步骤。所有这些历史都占用上下文窗口的空间，并可能通过提供过时信息积极误导 Agent。

ACI 的上下文管理系统将较旧的观察（最近五轮之前的）折叠为单行摘要。这让活跃的上下文聚焦于最近的、相关的信息，同时保留了整体轨迹的压缩记录。Agent 始终可以看到它最近做了什么以及当前状态是什么，而不被它曾经运行的每个命令的完整未压缩历史所埋没。

## 基准测试结果及其真正含义

SWE-agent 论文在 SWE-bench 数据集上对其 ACI 进行了基准测试，该数据集是来自流行 Python 仓库的真实 GitHub Issue 集合。任务是接收自然语言的 bug 报告并生成解决它的代码补丁。

使用 GPT-4 配合标准 bash shell 接口，系统解决了 3.97% 的问题。使用 GPT-4 配合专门构建的 ACI，系统解决了 12.47% 的问题。这就是前面提到的 64% 相对提升，完全来自接口设计。

性能差异不在于模型智能。而在于认知负荷管理。ACI 减少了模型需要做的状态追踪工作，为真正重要的工作腾出了空间。

这些影响远远超出编码 Agent。任何长周期 Agent 任务都涉及相同的根本挑战：导航大型信息空间、在多个步骤中维护连贯状态、捕获并从错误中恢复，以及管理有限的上下文窗口注意力资源。ACI 设计原则可以泛化。具体工具会变。问题的底层架构不会变。

# 第三部分：Anthropic 的 Harness 工程（长时间运行 Agent 问题）

## 为什么上下文窗口边界才是真正的难题

SWE-agent 论文解决了如何为单个 Agent 会话设计接口。Anthropic 的工程团队在开发 Claude Agent SDK 和 Claude Code 时遇到了不同的问题：当一个任务大到无法在单个上下文窗口中完成时会发生什么？

这不是小众边缘情况。大多数真实的软件项目都大到任何上下文窗口都装不下。即使有 200K token 的上下文窗口，你也无法同时将整个项目记在脑中。人类工程师通过外部记忆、文档、版本控制和在代码库中工作数周数月积累的理解来解决这个问题。一个开始新会话的 Agent 什么都没有。

天真的解决方案是压缩（compaction），它在一定程度上有效。但仅靠压缩是不够的。Anthropic 的内部实验表明，即使有压缩，像 Opus 4.5 这样的前沿编码模型在多个上下文窗口的循环中运行，也会始终无法从高层级提示词构建出生产级质量的 Web 应用。

失败聚集在两种模式上：

第一种失败模式是试图一次做太多。当给出「构建一个 claude.ai 的克隆」这样的提示词时，Agent 会试图一次性完成整个应用。它会一个接一个地开始实现功能而不完成或测试任何一个，在实现过程中耗尽上下文窗口，让下一个会话面对一个半实现的应用——没有文档记录做了什么，也没有清楚指示代码的状态。下一个 Agent 实例会花大部分上下文预算来理解这个烂摊子，而不是取得进展。

第二种失败模式出现在项目后期。在一些功能构建完成后，后续的 Agent 实例会四处查看，看到已经取得了进展，就得出工作已完成的结论。它会在部分完成的应用上宣布胜利并停止工作。这不是愚蠢，而是基于不完整信息的合理推断——Agent 没有结构化的方式来知道「完成」对这个项目到底意味着什么。

两种失败共享一个根本原因：Agent 没有持久的、结构化的项目状态理解，这种理解能跨越上下文窗口边界并指导未来的会话。

## 双 Agent 架构：初始化 Agent 和编码 Agent

Anthropic 的解决方案是一个两部分架构，后来成为认真对待长时间运行 Agent 工作的团队的模板。

第一部分是初始化 Agent。这是一个带有独特系统提示词的专门化首次会话，其唯一目的是建立所有未来编码 Agent 将在其中运行的环境。它不写功能，它创建使跨多个后续会话的功能开发成为可能的脚手架。

初始化 Agent 产生三个关键输出。首先，它创建一个 init.sh 脚本来可靠地启动开发环境。每个后续编码 Agent 会话都可以通过运行 init.sh 开始，而不是花 token 来弄清楚如何启动。

其次，初始化 Agent 创建一个全面的功能列表文件。在 Anthropic 内部运行的 claude.ai 克隆实验中，这意味着超过 200 个具体的、端到端的功能描述。每个功能最初标记为失败。这个文件作为项目的事实来源。一个开始新会话的编码 Agent 读取这个文件就能立即确定什么已经构建了，什么还没有。

第三，初始化 Agent 创建一个 claude-progress.txt 文件并进行初始 git 提交。进度文件是一个人类可读的日志，Agent 在每个会话结束时更新，记录它做了什么、完成了什么、以及它将事情留在了什么状态。

## 功能列表作为认知锚点

功能列表值得特别关注，因为它解决了一个容易被低估的问题。没有它，在复杂代码库中运行的 Agent 必须从代码本身推断项目的完成度。这种推断是不可靠的。

功能列表使完成度变得明确且无歧义。每个功能有一个 passes 字段，要么是 true 要么是 false。没有歧义，不需要推断。事实来源就在文件中。

Anthropic 做了一个深思熟虑的决定，用 JSON 而不是 Markdown 存储这个列表。原因是行为层面的。经验表明，模型不太可能不当修改或覆盖 JSON 文件。JSON 具有严格的结构，抵抗随意编辑。

## 增量进展与干净状态要求

多会话 Agent 工作中最难的问题之一是确保每个会话结束在下一个会话可以安全构建的状态。Anthropic 的解决方案是将干净状态作为一等要求。每个编码 Agent 会话以 git 提交（带描述性消息）、进度文件更新以及必要时回退到工作状态结束。

git 提交不仅是检查点，还是恢复机制。当 Agent 做出破坏性更改时，它可以使用 git 回退到上一个已知良好状态并重试。版本控制是认知脚手架，不仅仅是源代码管理。

## 测试：没人愿意谈论的失败模式

Anthropic 记录了一个几乎在每个严肃的 Agent 编码项目中都会出现的失败模式：Agent 在没有正确端到端验证的情况下将功能标记为完成。

解决方案是给 Agent 访问 Puppeteer MCP 服务器的权限——一个浏览器自动化工具，允许 Claude 实际导航应用、点击按钮、填写表单并验证功能端到端工作。性能提升是戏剧性的。

这是一个一般原则的具体例证：Agent 的工作质量受限于其反馈循环的质量。如果你的 Agent 无法在重要领域观察其行为的后果，它将优化可能与实际正确性无关的代理指标。

# 第四部分：OpenAI 的 Harness 工程（零行手动代码）

## 实验

2025 年 8 月下旬，OpenAI 的 Codex 团队启动了一个 git 仓库，只有一个约束：没有人工编写的代码。仓库中的每一行代码——包括应用逻辑、测试、CI 配置、文档、可观测性工具和内部开发者工具——都由 Codex Agent 编写。人类负责引导，Agent 负责执行。

五个月后，仓库包含大约一百万行代码。约 1500 个 Pull Request 已被打开和合并。一个三人的小团队驱动了其中大部分，平均每人每天 3.5 个 PR。随着团队增长到七人，每人的产出实际上还增加了。

这不是演示。这是一个完全通过 Agent 生成代码构建和交付的真正的内部产品。中心信息与 SWE-agent 论文相同：瓶颈从来不是模型能力，瓶颈始终是环境设计。

## 工程工作的重新定义

最重要的观察是关于工程工作本身如何改变的。当你的主要工作不再是写代码时，你在做什么？

你在设计环境。你在明确意图。你在构建反馈循环。你不断地问的不是「我如何修复这个 bug？」而是「环境中缺少什么能力导致了这个 bug 的出现？」

当某件事失败时，修复几乎从来不是「更努力地尝试」。它几乎总是「环境中缺少或配置错误的什么结构性部分导致了 Agent 在这里失败？」这是工程思维的深刻转变。你不再调试代码，你开始调试产生代码的系统。

## 仓库知识作为事实系统

最重要的架构决策之一是让仓库本身成为 Agent 需要知道的一切的事实来源。洞察很简单但影响深远：从 Agent 的角度来看，它在运行时无法在上下文中访问的任何东西实际上就不存在。

项目早期，团队尝试了「一个大的 AGENTS.md」方法——一个包含 Agent 需要知道的关于项目一切的单一大型指令文件。它以可预见的方式失败了：首先，上下文是稀缺资源，巨大的指令文件挤占了任务、代码和相关文档；其次，太多指导变成了无指导；第三，它会立即腐烂；第四，它难以验证。

解决方案是一个结构化的 docs/ 目录作为事实系统，配合一个简短的 AGENTS.md 文件（约 100 行）作为指向更深层事实来源的地图。这实现了团队所说的渐进式披露：Agent 从一个小而稳定的入口点开始，被教导在需要时去哪里查看更多信息，而不是一开始就被淹没。

## 应用可读性：让系统对 Agent 可见

随着代码产出增加，瓶颈从生成转移到了验证。团队生成代码的速度超过了人工 QA 的验证能力。解决方案是让更多的验证工作成为 Agent 自己能做的事情。

他们让应用可以按 git worktree 启动，让 Codex 能为每个正在处理的变更启动和驱动应用的隔离实例。他们将 Chrome DevTools Protocol 接入 Agent 运行时。他们构建了完整的本地可观测性栈：日志、指标和追踪通过 LogQL、PromQL 和 TraceQL 暴露给 Codex。

## 在不微观管理的情况下执行架构

完全由 Agent 生成的代码库中最有趣的挑战之一是随时间保持架构一致性。OpenAI 的解决方案是通过机械手段而非人工代码审查来执行不变量。

应用围绕严格的架构模型构建：每个业务域分为固定的层集合，具有严格验证的依赖方向和有限的允许边集合。这些约束由自定义 linter（自然是由 Codex 编写的）和结构性测试执行。

关键洞察是在边界内执行的同时允许边界内的显著自由。这与使平台团队在规模上有效的原则相同：执行基础，允许其上的自主权。

## 产出改变了合并哲学

当 Agent 产出大幅超过人类注意力容量时，传统的工程规范变得适得其反。OpenAI 的团队做出了刻意的决定：以最少的阻塞合并门运作。PR 保持短生命周期。测试不稳定通过后续运行解决，而不是无限期阻塞进展。

当 Agent 产出远超人类注意力时，修正是廉价的而等待是昂贵的。正确的权衡在低产出环境中看起来不负责任，在高产出环境中则显而易见。

# 第五部分：Agent Harness 分类体系

## 生态系统映射

Awesome Agent Harness 仓库试图映射新兴的 Harness 工程工具生态系统。其核心论点值得在深入分类之前明确说明：AI 编写代码的能力实际上已经是商品化的。基础模型可以生成功能性代码，这不再是差异化的能力。差异化的能力在于协调和环境设计。

该仓库将完整的 Harness 生态系统分为七个不同的层。

第一层：人类监督

顶层是人类监督层，人类在这里批准提案、审查 PR 和设定优先级。关键设计原则是工程师应该设计环境和审查结果，而不是直接编写代码。他们的杠杆来自引导，而不是执行。

第二层：规划和需求（Spec 工具）

这一层将人类的想法转化为 Agent 可以可靠消费的结构化规格说明和任务 DAG。底层洞察是 Agent 盲目执行。如果规格说明模糊或歧义，Agent 会产出满足其对规格说明的解释的东西，而这可能不是人类的意图。

第三层：全生命周期平台

这些工具管理从初始需求到交付的端到端流程，将 AI 提案与人类验证门和子 Agent 编排集成。

第四层：任务运行器

任务运行器弥合了 Issue 追踪器（GitHub Issues、Linear）和编码 Agent 之间的差距。流程是：人类或 PM Agent 创建 Issue，任务运行器生成工作空间，Agent 交付 PR，人类审查。

第五层：Agent 编排器

编排器通过在独立的 git worktree 中隔离工作来实现多个 Agent 的并行执行，解决产出问题。这至关重要，因为在同一工作区并行工作的 Agent 如果共享工作空间会互相冲突。

第六层：Agent Harness 框架和运行时

框架提供构建自定义环境的可组合原语：渐进式披露机制、子 Agent 生成、结构化上下文交付。运行时提供持久化基础设施：长期运行的记忆、定时执行、会话间的多通道通信。框架是你构建的基础，运行时是持续运行的东西。两者对于严肃的长期 Agent 工作都是必要的。

第七层：编码 Agent

底层是执行层：Claude Code、Codex 和类似的系统。仓库的关键洞察是这一层是商品。Agent 的效果主要由其上方的所有层决定，而不是 Agent 本身。

# 第六部分：反复出现的设计模式

在所有这些系统和组织中，几种设计模式反复出现。它们不是巧合，而是在你试图大规模可靠部署 Agent 时出现的问题的工程解决方案。

## 模式一：渐进式披露

不要预先给 Agent 所有它可能需要的东西。给它最少的定向信息和在需要时找到更多信息的指针。这个模式出现在 SWE-agent 的有上限搜索中、OpenAI 的 docs/ 架构中、Anthropic 的启动序列中，以及实现结构化上下文分层的 Harness 框架中。

认知原因：上下文是有限资源，Agent 的注意力在上下文中的分布不均匀。提示词开头的信息具有不成比例的影响力。一个简短、聚焦的入口点加上指向更丰富上下文的指针，比一次性全量转储更有效。

## 模式二：Git Worktree 隔离

一个 Agent，一个 worktree。这个模式出现在每个严肃的编排系统中。当你有多个 Agent 并行工作时，你需要工作流之间的隔离。Git worktree 在文件系统级别提供这种隔离。每个 Agent 获得自己的工作目录、自己的分支和自己的环境。

## 模式三：Spec 优先，仓库作为事实系统

Agent 对非正式知识是盲目的。活在 Slack 线程、Google Doc 或某人脑中的东西对 Agent 来说不可见。Agent 能使用的唯一东西是其上下文窗口中的内容，而该上下文唯一可靠的来源是仓库。

文档不再只面向人类读者。它是人类意图对 Agent 变得可读的机制。模糊的、陈旧的或存储在仓库外的文档是积极损害 Agent 性能的文档。

## 模式四：机械化架构执行

人工代码审查无法扩展到 Agent 驱动的开发。当 Agent 每天能为每个工程师开 3.5 个 PR 时，审查不能成为维护代码质量和架构完整性的主要机制。解决方案是将架构约束编码为自动运行的机械检查。

关键设计原则是执行不变量，而不是实现。你深切关注依赖方向、边界穿越、接口处的数据验证。你不关心 Agent 使用哪个具体库或函数如何精确分解，只要它满足行为契约。

## 模式五：集成反馈循环

每个高性能的 Harness 架构都尽可能紧密地关闭反馈循环。编辑时的语法错误由 linter 捕获；运行时错误通过 Agent 可查询的可观测性工具暴露；UI bug 通过 Agent 可驱动的浏览器自动化捕获。

这是经典软件工程原则的 Harness 版本——越早捕获错误，修复成本越低。对于 Agent，这一原则适用得更强，因为未被立即捕获的错误会在上下文中累积并降低后续推理的质量。

# 第七部分：这对工程师到底意味着什么

## 可迁移的技能

Harness 工程学科本质上是应用于 Agent 环境的系统思维。它要求你足够理解语言模型的认知架构，以设计与之协作而非对抗的环境。它要求你以分布式系统工程熟悉的方式思考状态管理、反馈循环、错误恢复和上下文优化——但应用到一个新的领域。

在这个新兴范式中最有效的工程师不是那些拥有最佳提示词技巧的人。他们是理解整个系统如何工作的人：上下文如何流动、在哪里被破坏、反馈循环如何收紧、状态如何跨会话保持、约束如何在不微观管理 Agent 行为的情况下执行。

## 你应该问的问题

当你构建 Agent 系统而某些东西不工作时，Harness 工程思维产生的问题集与天真思维不同。

不要问「我如何写更好的提示词？」而是问「Agent 需要什么当前无法访问的信息？」不要问「为什么模型犯了这个错？」而是问「缺少什么反馈循环来在错误传播前捕获它？」不要问「为什么 Agent 没做我让它做的？」而是问「环境中什么约束阻止了 Agent 做我让它做的？」

这种转变不仅是语义上的。它改变了你投入工程努力的方向。投资于解决这个特定失败模式的更好提示词是局部的和暂时的。投资于防止一类失败模式的更好工具是通用的和永久的。Harness 是那个永久投资的所在。

## 执行的商品化

如果执行层是商品，那么 AI 驱动开发中的长期竞争护城河不在于模型，而在于 Harness。

这意味着投资于 Harness 工程——构建脚手架、反馈循环、可观测性、Spec 工具和编排——允许 Agent 大规模可靠工作的组织和个人，将比那些主要关注使用哪个模型或如何提示它的人拥有持久的优势。

模型是进行思考的东西。Harness 是思考的内容。搞清楚这个区别就是全部的游戏。

# 第八部分：构建你自己的 Harness

## 最小 Harness

你不需要构建 OpenAI 的可观测性栈或 Anthropic 的完整双 Agent 架构来从 Harness 思维中获益。真实项目上编码 Agent 的最小有效 Harness 只有几个基本组件。

从一个持久的进度文件开始。Agent 在每个会话开始时读取它以了解上次做了什么，在每个会话结束时写入它以记录做了什么。这个单一变更就能防止「过早宣布胜利」的失败模式。

添加一个结构化的任务列表。不是项目的模糊描述，而是可验证的完成标准的具体、编号列表。每个条目描述可端到端测试的用户可见行为。

将版本控制和描述性提交消息作为每个会话的一等组成部分。每个会话以提交结束。

如果你在构建 Web 应用，添加浏览器自动化。大多数重要的 bug 只在运行时可见。

## 环境审计

如果你已经有了一个 Agent 系统而它表现不佳，Harness 工程方法建议一个具体的诊断流程。不要去拿更好的模型或更长的提示词，做一个环境审计。

问：Agent 需要什么它当前无法访问的信息？任务流中 Agent 经常卡住或犯错的地方在哪里？缺少什么反馈可以让 Agent 自己捕获那些错误？上下文在哪里被不相关的信息污染？哪些约束需要被执行但目前依赖于 Agent 的判断？

这就是 Harness 开发的良性循环：每次失败都是关于环境需要什么的信号，环境的每次改进都会在所有未来 Agent 会话中减少该失败的频率。

# 最后的话

变革性技术在早期阶段如何被误解，有一种规律。吸引公众注意力的东西——原始能力、令人印象深刻的演示、基准分数——很少是长期决定谁赢的东西。基础设施层——Harness、环境——通常才是真正的价值被创造和获取的地方。

Web 的变革性不是因为 HTML 存在，而是因为搜索引擎和浏览器使 Web 可导航。移动的变革性不是因为智能手机存在，而是因为应用商店和开发者工具使大规模构建成为可能。在两种情况下，组织底层能力的平台层才是持久价值的所在。

AI Agent 正在遵循相同的模式。能力已经存在。问题是谁构建了使能力可靠、可控和可持续改进的环境。

Harness 才是一切。模型是推理引擎。Harness 是上下文、约束、反馈循环、记忆、工具和脚手架——它决定了推理引擎实际上能完成什么。搞对 Harness 不是一个提示词工程问题。它是一个系统工程问题。而且是当前应用 AI 中最重要的工程问题。

据此行动。
