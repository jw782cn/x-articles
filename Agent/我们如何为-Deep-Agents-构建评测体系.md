## Eval 塑造 agent 行为

我们一直在策划评测来衡量和改进 Deep Agents。Deep Agents 是一个开源的、模型无关的 agent 框架，驱动着 Fleet 和 Open SWE 等产品。Eval 定义和塑造 agent 行为，这就是为什么精心设计它们如此重要。

每一个 eval 都是一个向量，会改变你的 agentic 系统的行为。例如，如果一个测试高效文件读取的 eval 失败了，你可能会调整 system prompt 或 read_file 工具的描述来引导行为，直到它通过为止。你保留的每一个 eval 都会随着时间推移对整个系统施加压力。

在添加 eval 时，深思熟虑至关重要。盲目添加数百（甚至数千）个测试是很诱人的。但这会产生一种"在提升 agent"的幻觉，因为你可能在一个并不能准确反映生产环境中你关心的行为的 eval 套件上取得了高分。

更多 eval ≠ 更好的 agent。相反，要构建能反映生产环境中期望行为的、有针对性的 eval。

在构建 Deep Agents 时，我们会梳理生产环境中重要的行为，比如跨文件系统中多个文件检索内容，或者准确地串联执行 5 个以上的工具调用。我们没有笼统地使用基准测试任务，而是采用以下方式来策划 eval：

## Dogfooding agent 和阅读 trace 是 eval 的绝佳来源

这让发现错误成为可能。Trace 给我们提供了理解 agent 行为的数据。因为 trace 通常很大，我们使用内置的 agent（如 Polly 或 Insights）来大规模分析它们。你也可以用其他 agent（如 Claude Code 或 Deep Agents CLI）加上拉取 trace 的工具（如 LangSmith CLI）来做同样的事。我们的目标是理解每种失败模式，提出修复方案，重新运行 agent，并随着时间推移追踪进展和回归。

例如，现在有大量的 bug 修复 PR 是通过 Open SWE（我们的开源后台编码 agent）驱动的。使用它的团队涉及许多不同的代码库，有着不同的上下文、规范和目标。这自然会导致错误。Open SWE 的每一次交互都会被记录 trace，因此这些 trace 可以很容易地变成 eval，确保同样的错误不会再次发生。

其他 eval 则从现有基准测试中拉取和调整，比如用于函数调用的 BFCL。对于编码任务，我们集成了 Harbor，在沙箱环境中运行 Terminal Bench 2.0 等数据集中的选定任务。许多 eval 是从零开始编写的，作为专注测试来观察隔离的行为，比如测试 read_file 工具。

## 我们如何定义指标

在为 agent 选择模型时，我们从正确性开始。如果一个模型不能可靠地完成我们关心的任务，其他一切都不重要。我们在 eval 上运行多个模型，并随着时间推移不断优化框架，以解决我们发现的问题。

衡量正确性取决于被测试的内容。大多数内部 eval 使用自定义断言，比如"agent 是否并行化了工具调用？"。像 BFCL 这样的外部基准测试使用数据集中的 ground truth 答案进行精确匹配。对于正确性是语义层面的 eval（比如 agent 是否在 memory 中持久化了正确的内容），我们使用 LLM-as-a-judge。

一旦几个模型通过了这个门槛，我们就转向效率。两个解决同一任务的模型在实践中的表现可能大相径庭。一个可能需要额外的轮次，做出不必要的工具调用，或者因为模型体积大而更慢地完成任务。在生产环境中，这些差异表现为更高的延迟、更高的成本，以及更差的整体用户体验。

## 围绕 eval 的实用指标示例

为了让模型对比具有可操作性，我们需要检查模型如何成功和失败。这需要一个具体的参考点来定义什么是"好"的执行，而不仅仅是准确率。我们使用的一个基本概念是 ideal trajectory（理想轨迹）。它是一系列产生正确结果且没有"不必要"操作的步骤序列。

对于简单的、范围明确的任务，变量定义得足够严格，最优路径通常是显而易见的。对于更开放性的任务，我们使用到目前为止表现最好的模型来近似一个 trajectory，然后随着模型和框架的改进重新审视基线。通过这种方式，观察 agent 行为帮助我们优化对 ideal trajectory 的先验认知。

## 我们如何运行 eval

我们使用 pytest 配合 GitHub Actions 在 CI 中运行 eval，这样变更可以在一个干净的、可复现的环境中运行。每个 eval 创建一个使用给定模型的 Deep Agent 实例，给它一个任务，并计算正确性和效率指标。

我们还可以使用标签运行 eval 的子集，以节省成本并衡量有针对性的实验。例如，如果构建一个需要大量本地文件处理和合成的 agent，我们可能会专注于 file_operations 和 tool_use 标签的子集。
