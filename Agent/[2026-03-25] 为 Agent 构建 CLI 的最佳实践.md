# [2026-03-25] 为 Agent 构建 CLI 的最佳实践

**原文链接**：[Building CLIs for agents](https://x.com/ericzakariasson/status/2036762680401223946) by **@ericzakariasson****48万阅读** | **1815点赞** | **3179收藏**

如果你曾经看过一个 Agent 试图使用 CLI，你一定见过它卡在某个交互式提示上无法回答，或者费力解析一个没有示例的帮助页面。大多数 CLI 在设计时都假设键盘前坐着的是一个人类。以下是我总结的一些让 CLI 更好地服务于 Agent 的实践经验：

**让它非交互化。** 如果你的 CLI 在执行过程中突然弹出一个交互提示，Agent 就卡住了。它没法按方向键，也没法在正确的时机输入 "y"。每个输入都应该可以通过 flag 传递。把交互模式作为缺少 flag 时的兜底方案，而不是主要路径。

**不要一上来就倾倒所有文档。** Agent 运行 mycli，看到子命令列表，选一个，然后运行 mycli deploy --help，得到它需要的信息。不会在它用不到的命令上浪费 context。让它按需逐步发现。

**让 --help 真正有用。** 每个子命令都要有 --help，每个 --help 都要包含示例。示例承担了大部分工作。Agent 从 mycli deploy --env staging --tag v1.2.3 这样的例子中做模式匹配，比读一段描述文字快得多。

**所有输入都支持 flag 和 stdin。** Agent 的思维方式是 pipeline。它们想要串联命令、在工具之间传递输出。不要要求奇怪顺序的位置参数，也不要在缺少值时回退到交互式提示。

**快速失败，给出可操作的错误信息。** 如果缺少必需的 flag，不要挂起。立即报错并展示正确的调用方式。当你给 Agent 提供可以参考的信息时，它们非常擅长自我纠正。

**让命令具备幂等性。** Agent 会不断重试。网络超时、任务中途丢失 context，这些都很常见。同一个 deploy 命令跑两次，应该返回 "already deployed, no-op"，而不是创建一个重复项。

**为破坏性操作添加 --dry-run。** Agent 应该能够在真正执行之前预览 deploy 或删除操作会做什么。让它先验证计划，然后再真正执行。

**用 --yes / --force 跳过确认。** 人类看到 "are you sure?"，Agent 则传 --yes 来跳过。让安全路径成为默认选项，但允许绕过。

**可预测的命令结构。** 如果 Agent 学会了 mycli service list，它应该能猜到 mycli deploy list 和 mycli config list。选定一个模式（资源 + 动词），然后在所有地方统一使用。

**成功时返回数据。** 展示 deploy ID 和 URL。Emoji 很可爱，但并不是真正需要的。

如果你正在构建 Agent 会使用的 CLI，这些模式能帮你省下大量调试时间。大部分工作其实就是把人类隐式理解的东西显式化而已！

我相信还有很多我遗漏的点，欢迎补充！

**核心观点**：为 Agent 设计 CLI 的关键在于"显式化"——非交互、幂等、可预测的命令结构、有示例的帮助文档、可操作的错误信息。本质上就是把人类凭直觉理解的东西，变成机器能可靠解析的接口。
