# [2026-03-25] 长时间运行应用开发的 Harness 设计

**原文链接**：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) by **Prithvi Rajasekaran @AnthropicAI**

作者 Prithvi Rajasekaran，Anthropic [Labs](https://www.anthropic.com/news/introducing-anthropic-labs) 团队成员。

过去几个月里，我一直在研究两个相互关联的问题：让 Claude 产出高质量的前端设计，以及让它在没有人工干预的情况下构建完整的应用。这项工作源于我们此前在[前端设计技能](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)和[长时间运行编码 Agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 上的探索——在那些工作中，我和同事们通过 prompt 工程和 harness 设计将 Claude 的表现提升到了远超基线的水平，但最终都触及了天花板。

为了突破瓶颈，我寻找了在两个截然不同领域都能成立的新型 AI 工程方法——一个领域由主观审美定义，另一个则由可验证的正确性和可用性定义。受到[生成对抗网络](https://en.wikipedia.org/wiki/Generative_adversarial_network)（GAN）的启发，我设计了一个包含 generator 和 evaluator agent 的多 agent 架构。要构建一个能可靠打分且具有审美品味的 evaluator，首先需要开发一套评判标准，将"这个设计好不好？"这样的主观判断转化为具体的、可评分的维度。

随后我将这些技术应用到了长时间运行的自主编码任务中，延续了我们早期 harness 工作的两个经验：将构建过程分解为可管理的小块，以及使用结构化产物在不同会话间传递上下文。最终成果是一个三 agent 架构——planner、generator 和 evaluator——能够在多小时的自主编码会话中产出丰富的全栈应用。

## 为什么朴素的实现方式行不通

我们此前已经证明，harness 设计对长时间运行 agent 编码的效果有着重大影响。在一次早期的[实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)中，我们使用了一个 initializer agent 将产品规格分解为任务列表，以及一个 coding agent 逐个实现功能，并在会话间通过产物传递上下文。更广泛的开发者社区也收敛到了类似的洞察，比如"[Ralph Wiggum](https://ghuntley.com/ralph/)"方法，使用 hooks 或脚本让 agent 保持持续的迭代循环。

但一些问题始终存在。对于更复杂的任务，agent 仍然会随着时间推移逐渐偏离轨道。在分析这个问题时，我们观察到 agent 执行此类任务时的两种常见失败模式。

第一种是模型在执行长任务时，随着上下文窗口被填满，往往会失去连贯性（参见我们关于[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)的文章）。某些模型还表现出"上下文焦虑"——当它们认为自己接近上下文限制时，会过早地开始收尾工作。上下文重置——彻底清空上下文窗口并启动一个全新的 agent，同时通过结构化交接传递前一个 agent 的状态和后续步骤——可以同时解决这两个问题。

这与 compaction 不同。Compaction 是将对话早期部分原地压缩摘要，让同一个 agent 在缩短的历史上继续工作。虽然 compaction 保留了连续性，但它没有给 agent 一个全新的开始，这意味着上下文焦虑仍然可能存在。重置提供了一个干净的起点，代价是交接产物需要包含足够的状态信息，让下一个 agent 能顺利接手工作。在我们早期的测试中，Claude Sonnet 4.5 表现出的上下文焦虑非常强烈，仅靠 compaction 不足以支撑长任务的良好表现，因此上下文重置成为了 harness 设计的关键要素。这解决了核心问题，但也为每次 harness 运行增加了编排复杂度、token 开销和延迟。

第二个问题是我们此前尚未解决的——自我评估。当被要求评估自己产出的工作时，agent 往往会自信满满地夸赞自己的成果——即使在人类观察者看来，质量明显平庸。这个问题在设计这类主观任务上尤为突出，因为没有等同于可验证软件测试的二元检查方法。一个布局看起来是精致还是平庸，这是一个判断问题，而 agent 在给自己的工作打分时会可靠地偏向正面。

然而，即使在有可验证结果的任务上，agent 有时仍会表现出糟糕的判断力，影响它们完成任务时的表现。将执行工作的 agent 与评判工作的 agent 分离，被证明是解决这个问题的有力杠杆。这种分离本身并不能立即消除宽容倾向——evaluator 仍然是一个倾向于对 LLM 生成内容持宽容态度的 LLM。但将一个独立的 evaluator 调教为持怀疑态度，比让 generator 对自己的工作保持批判性要容易得多，而一旦有了外部反馈，generator 就有了具体的迭代目标。

## 前端设计：让主观质量变得可评分

我从前端设计开始实验，因为自我评估问题在这里最为明显。在没有任何干预的情况下，Claude 通常会倾向于安全、可预测的布局——技术上能用，但视觉上平淡无奇。

构建前端设计 harness 的两个关键洞察。第一，虽然审美不能完全简化为一个分数——个人品味总会有差异——但可以通过编码设计原则和偏好的评分标准来提升。"这个设计美不美？"很难给出一致的回答，但"这个设计是否遵循了我们的好设计原则？"给了 Claude 一个具体的评判依据。第二，通过将前端生成与前端评分分离，我们可以创建一个反馈循环，推动 generator 产出更强的结果。

我使用带有详细评分分解的 few-shot 示例来校准 evaluator。这确保了 evaluator 的判断与我的偏好一致，并减少了跨迭代的分数漂移。

我在 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 上构建了这个循环，编排过程因此保持了简洁。Generator agent 首先根据用户 prompt 创建一个 HTML/CSS/JS 前端。我给了 evaluator Playwright MCP，让它能在打分和撰写详细评审之前直接与实时页面交互。在实践中，evaluator 会自主浏览页面，截图并仔细研究实现细节，然后给出评估。这些反馈作为下一次迭代的输入回流到 generator。我每次生成运行 5 到 15 次迭代，每次迭代通常会推动 generator 朝着更独特的方向发展，因为它在回应 evaluator 的评审。由于 evaluator 是在主动浏览页面而非评分静态截图，每个循环都需要真实的时间。完整运行最长可达四小时。我还指导 generator 在每次评估后做出策略决策：如果分数趋势向好则继续优化当前方向，如果当前方法行不通则转向完全不同的审美风格。

在多次运行中，evaluator 的评估在迭代过程中先提升后趋于平稳，且仍有提升空间。有些生成过程是渐进式优化，另一些则在迭代之间发生了大幅审美转变。

评分标准的措辞对 generator 的引导方式超出了我的预期。像"最好的设计应该达到博物馆级品质"这样的表述推动设计走向了特定的视觉收敛，表明评分标准中的 prompt 措辞直接塑造了产出的特征。

虽然分数总体上随迭代提升，但模式并不总是线性的。后期的实现整体往往更好，但我经常看到中间某次迭代比最后一次更合我心意的情况。实现复杂度也倾向于在各轮中递增，generator 为回应 evaluator 的反馈而尝试更大胆的方案。即使在第一次迭代中，产出也明显优于完全没有 prompt 的基线，这表明评分标准及其相关描述语言本身就在 evaluator 反馈带来进一步优化之前，将模型从通用默认值中拉了出来。

一个值得注意的例子：我让模型创建一个荷兰艺术博物馆网站。到第九次迭代时，它已经为一个虚构博物馆制作了一个简洁的深色主题登陆页。页面视觉上很精致，但基本在我的预期之内。然后，在第十个循环中，它彻底推翻了之前的方案，将网站重新构想为一个空间体验：一个用 CSS 透视渲染的棋盘格地板 3D 房间，画作以自由布局挂在墙上，通过门廊式导航在画廊房间之间穿梭，而不是传统的滚动或点击。这种创造性跳跃是我在单次生成中从未见过的。

## 扩展到全栈编码

有了这些发现，我将这种受 GAN 启发的模式应用到了全栈开发中。Generator-evaluator 循环天然映射到软件开发生命周期中，其中代码审查和 QA 承担着与设计 evaluator 相同的结构性角色。

### 架构

在我们早期的[长时间运行 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 中，我们通过 initializer agent、逐功能工作的 coding agent 以及会话间的上下文重置，解决了多会话编码的连贯性问题。上下文重置是关键突破：harness 使用的 Sonnet 4.5 表现出前文提到的"上下文焦虑"倾向。设计一个能在上下文重置间良好运行的 harness，是让模型保持专注的关键。Opus 4.5 很大程度上自行消除了这种行为，因此我得以从这个 harness 中完全去掉上下文重置。Agent 在整个构建过程中作为一个连续会话运行，由 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 的自动 compaction 处理上下文增长。

在这项工作中，我在原始 harness 的基础上构建了一个三 agent 系统，每个 agent 针对我在此前运行中观察到的特定缺陷。系统包含以下 agent 角色：

**Planner**：我们之前的长时间运行 harness 需要用户预先提供详细的规格说明。我想自动化这一步，所以创建了一个 planner agent，它接收简单的 1-4 句 prompt 并将其扩展为完整的产品规格。我在 prompt 中要求它在范围上要有野心，并专注于产品上下文和高层技术设计，而非详细的技术实现。之所以这样强调，是因为如果 planner 试图预先指定细粒度的技术细节却出了错，规格中的错误会级联传导到下游实现中。更明智的做法是约束 agent 需要交付什么，让它们在工作过程中自行摸索路径。我还要求 planner 寻找机会将 AI 功能编织进产品规格中。（示例见文末附录。）

**Generator**：早期 harness 中逐功能推进的方式在范围管理上效果不错。我在这里采用了类似模型，指导 generator 以 sprint 方式工作，每次从规格中选取一个功能来实现。每个 sprint 使用 React、Vite、FastAPI 和 SQLite（后来改为 PostgreSQL）技术栈实现应用，generator 被指示在每个 sprint 结束时自评工作后再交给 QA。它还有 git 用于版本控制。

**Evaluator**：早期 harness 产出的应用常常看起来很炫，但当你真正尝试使用时还是有实际 bug。为了捕获这些问题，evaluator 使用 Playwright MCP 像用户一样点击浏览运行中的应用，测试 UI 功能、API 端点和数据库状态。然后它根据发现的 bug 以及一套从前端实验中改编的标准来给每个 sprint 打分，这里涵盖了产品深度、功能性、视觉设计和代码质量。每个标准都有一个硬性阈值，如果任何一项低于阈值，sprint 就会失败，generator 会收到关于问题所在的详细反馈。

在每个 sprint 之前，generator 和 evaluator 会协商一份 sprint 合约：在编写任何代码之前就"完成"的定义达成一致。之所以需要这样做，是因为产品规格是刻意保持高层次的，我需要一个步骤来弥合用户故事与可测试实现之间的差距。Generator 提出它要构建什么以及如何验证成功，evaluator 审查该提案以确保 generator 在构建正确的东西。双方迭代直到达成一致。

沟通通过文件处理：一个 agent 写文件，另一个 agent 读取并在该文件中回应，或者创建新文件供前一个 agent 读取。然后 generator 按照商定的合约进行构建，之后将工作交给 QA。这种方式让工作忠实于规格，同时不会过早地过度指定实现细节。

我期望的是一个界面：能让我构建关卡及其组成部分（精灵、实体、地块布局），然后点击播放来实际游玩关卡。我首先打开了单 agent 运行的产出，初始应用看起来符合这些期望。

然而随着我点击探索，问题开始浮现。布局浪费了空间，固定高度的面板让大部分视口空白。工作流程很死板。试图填充关卡时会提示我先创建精灵和实体，但 UI 中没有任何东西引导我按这个顺序操作。更关键的是，实际游戏是坏的。我的实体出现在屏幕上但没有任何东西响应输入。深入查看代码发现实体定义和游戏运行时之间的连线是断的，而且界面上没有任何迹象指明问题出在哪里。

评估完单 agent 运行后，我转向 harness 运行的结果。这次运行从同样的一句话 prompt 开始，但 planner 步骤将其扩展为一个跨十个 sprint 的 16 功能规格。它远远超出了单 agent 运行所尝试的范围。除了核心编辑器和游玩模式外，规格还包括精灵动画系统、行为模板、音效和音乐、AI 辅助的精灵生成器和关卡设计器，以及带分享链接的游戏导出功能。我给了 planner 我们的[前端设计技能](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)的访问权限，它读取后将其用于在规格中创建应用的视觉设计语言。每个 sprint 中，generator 和 evaluator 协商一份合约，定义该 sprint 的具体实现细节以及用于验证完成情况的可测试行为。

应用立即展现出比单 agent 运行更多的精致和流畅感。画布使用了整个视口，面板大小合理，界面有一致的视觉标识，与规格中的设计方向一脉相承。我在单 agent 运行中看到的一些笨拙感确实仍然存在——工作流仍然没有明确说明你应该先构建精灵和实体再尝试填充关卡，我得自己摸索。这读起来更像是基础模型在产品直觉方面的缺陷，而非 harness 设计要解决的问题，不过这确实提示了在 harness 内进行针对性迭代可以进一步提升产出质量的方向。

在编辑器中深入操作后，新运行相对于单 agent 的优势更加明显。精灵编辑器更丰富、功能更完善，工具面板更整洁，颜色选择器更好，缩放控制更易用。

因为我要求 planner 将 AI 功能编织进规格，应用还内置了 Claude 集成，让我可以通过 prompt 生成游戏的不同部分。这大大加速了工作流程。

最大的区别在游玩模式中。我实际上能够移动实体并游玩游戏。物理引擎有一些粗糙的地方——我的角色跳上平台后与之重叠了，这在直觉上感觉不对——但核心功能是可以工作的，而单 agent 运行未能做到这一点。四处移动一会儿后，我确实遇到了 AI 游戏关卡构建的一些局限。有一堵我跳不过去的大墙，所以我被卡住了。这表明 harness 还可以处理一些常识性改进和边缘情况来进一步打磨应用。

### 迭代 harness

第一轮 harness 结果令人鼓舞，但也笨重、缓慢且昂贵。合乎逻辑的下一步是找到简化 harness 而不降低性能的方法。这部分是常识，部分是一个更普遍原则的体现：harness 中的每个组件都编码了一个关于模型自身无法做到什么的假设，这些假设值得压力测试——既因为它们可能是错误的，也因为随着模型的改进它们可能很快过时。我们的博客文章 [Building Effective Agents](https://www.anthropic.com/research/building-effective-agents) 将其背后的理念概括为"找到最简单的可行方案，只在需要时增加复杂度"，这是一个在任何维护 agent harness 的人身上都会反复出现的模式。

在我第一次尝试简化时，我大幅裁减了 harness 并尝试了一些有创意的新想法，但未能复现原始版本的性能。而且也变得很难分辨 harness 设计中哪些部分实际上是承重的，以及在哪些方面承重。基于这次经验，我转向了更系统的方法：每次只移除一个组件，然后审查它对最终结果的影响。

在进行这些迭代循环时，我们也发布了 Opus 4.6，这进一步激励了降低 harness 复杂度。有充分理由预期 4.6 需要的脚手架会比 4.5 少。引用我们的[发布博客](https://www.anthropic.com/news/claude-opus-4-6)："[Opus 4.6] 规划更谨慎，能更长时间地执行 agent 任务，在更大的代码库中运行更可靠，并且具有更好的代码审查和调试能力来捕获自己的错误。"它在长上下文检索方面也有了大幅改进。这些都是 harness 原本用来补充的能力。

### 移除 sprint 结构

我首先完全移除了 sprint 结构。Sprint 结构曾帮助将工作分解为模型可以连贯处理的小块。鉴于 Opus 4.6 的改进，有充分理由相信模型可以原生处理这项工作而无需这种分解。

我保留了 planner 和 evaluator，因为两者仍然带来明显的价值。没有 planner 的话，generator 会缩小范围：给它原始 prompt，它会直接开始构建而不先制定规格，最终创建出功能远不如 planner 规划的应用。

移除 sprint 结构后，我将 evaluator 改为在运行结束时进行一次性评估，而非按 sprint 打分。由于模型能力大幅提升，evaluator 的承重程度也因此改变，其价值取决于任务相对于模型自身可靠处理范围的位置。在 4.5 上，这个边界很近：我们的构建处于 generator 独自可以做好的边缘，evaluator 在整个构建过程中捕获了有意义的问题。在 4.6 上，模型的原始能力提升了，边界也向外移动。那些以前需要 evaluator 检查才能连贯实现的任务，现在通常在 generator 自身的处理范围之内，对于这个范围内的任务，evaluator 成了不必要的开销。但对于仍处在 generator 能力边缘的构建部分，evaluator 继续带来了实质性的提升。

实际含义是：evaluator 不是一个固定的是/否决策。当任务超出当前模型可靠独立完成的范围时，它才值得投入成本。

在结构简化的同时，我还添加了 prompt 来改进 harness 将 AI 功能构建到每个应用中的方式，具体来说是让 generator 构建一个能通过工具驱动应用自身功能的真正 agent。这需要真正的迭代，因为相关知识足够新，Claude 的训练数据覆盖很薄。但经过足够的调优，generator 已经能正确地构建 agent 了。

## 未来展望

随着模型不断改进，我们可以大致预期它们能够工作更长时间，处理更复杂的任务。在某些情况下，这意味着围绕模型的脚手架随时间推移会变得不那么重要，开发者可以等待下一个模型，看到某些问题自行解决。另一方面，模型越好，就有越多空间去开发能够完成超出模型基线能力的复杂任务的 harness。

基于此，这项工作中有几条值得延续的经验。对你所构建的模型进行实验、阅读它在真实问题上的 trace、调优其性能以达到你期望的结果——这始终是好的实践。在处理更复杂的任务时，有时可以通过分解任务并为问题的每个方面应用专门的 agent 来获得提升空间。当新模型发布时，重新审视 harness 通常是好的做法：剥离那些不再对性能起承重作用的部分，并添加新的部分来实现此前可能无法达到的更强能力。

从这项工作中，我的确信是：随着模型的改进，有趣的 harness 组合空间并不会缩小。相反，它在移动，而 AI 工程师的有趣工作在于不断找到下一个新颖的组合。
