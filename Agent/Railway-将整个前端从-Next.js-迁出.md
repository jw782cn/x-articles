# [2026-04-07] Railway 将整个前端从 Next.js 迁出

原文链接：Moving Railway's Frontend Off Next.js by @Railway52万阅读 | 3168点赞 | 1254收藏

Railway 的整个生产前端已经不再运行在 Next.js 上了。Dashboard、Canvas、railway.com，全部迁移到了 Vite + TanStack Router，而且我们只用了两个 PR 就完成了迁移，期间零停机。

## Next.js 曾经很好用，直到它不再适合我们

Next.js 帮助 railway.com 从零起步，成长为一个每月服务数百万用户的生产应用。它是一个优秀的框架，但它已经不再是最适合我们产品的那个了。

前端构建时间已经悄然突破了 10 分钟。其中 6 分钟是 Next.js 本身消耗的，有一半的时间卡在"finalizing page optimization"（最终页面优化）上。对于一个每天多次发布的团队来说，这种构建时间不是小麻烦，而更像是对每一次迭代征收的高额税。

Railway 的应用绝大部分是客户端渲染的。Dashboard 是一个富状态交互界面，Canvas 是实时的，WebSocket 无处不在。Next.js 的 Server-first 原语根本不是我们在用的东西，我们最终在 Pages Router 之上自行构建了一套抽象层，仅仅是为了支持框架本身没有按我们需要的方式处理的布局和路由需求。

我们仍然停留在 Pages Router 上，这让共享布局变得很 hacky。每一个布局模式都是拼凑上去的变通方案，而不是框架的一等公民能力。App Router 本可以解决其中一些问题，但它重度倾向于 Server-first 的模式，而我们的产品是刻意走客户端驱动路线的。采用 App Router 意味着要围绕一个我们根本不需要的范式重新构建整个应用。

## 为什么选择 TanStack Start + Vite

我们想要一个与我们实际开发方式匹配的技术栈：显式的、客户端优先的、迭代速度快的。更何况，我们真的很享受用它来开发。

对于产品团队而言，我们希望获得一些好用的特性，让我们不用去操心前端实现方式的问题，以下几点真正说服了我们：

我们团队中有几个人在假期试用了 TanStack Start，反馈是一致的：我们喜欢用它来开发。对于 Railway Dashboard 这样的产品来说，这和任何 benchmark 一样重要。

## 两个 PR，零停机

一旦做出了决定，我就开始动手了。在合并前的 squash 之前，我大概提交了几百个 commit。

迁移一个服务数百万用户、包含 200 多个路由的生产前端，通常需要数月的并行运行和增量切换。我们有 deadline，所以我用两个 Pull Request 搞定了。

PR 1 替换了所有 Next.js 特有的东西：next/image、next/head、next/router。每一个都被替换为原生浏览器 API 或框架无关的替代方案。这个 PR 不改变框架本身，只是移除了对它的每一个依赖，这样 PR 2 就可以做一次干净的切换。

PR 2 切换了框架。200 多个路由全部迁移完成。我们首先系统性地将所有非路由相关的逻辑从页面文件中提取到独立的 React 组件里，然后根据原始的页面树生成所有路由。

接着我们引入 Nitro 作为服务层，用 Nitro 配置替换了 next.config.js，将重定向（500 多条）、安全头和缓存规则整合到了一个地方。我们还用浏览器原生替代方案替换了 Next.js 之前提供 polyfill 的 Node.js API（Buffer、url.parse 等），这作为副作用让我们的代码更加干净了。

选在一个周日清晨合并。团队立刻开始 dogfood，在 Discord 开了一个实时作战室，当天就推送了一连串修复。零停机。

## 我们放弃了什么

当然，我们获得了一个更快、更显式的技术栈，但不是没有取舍。

## Railway 的前端跑在 Railway 上

我们以和用户完全相同的方式运行我们的生产前端：每个 PR 的 Preview Deploy、健康检查、零停机滚动更新。当我们替换了整个构建系统和框架时，我们没有动基础设施。我们改了代码，推上去，Railway 搞定了剩下的一切。

Fastly 现在直接从边缘节点服务我们大部分的流量。营销页面被缓存，动态页面在需要时使用 ISR，因此我们的前端服务器基本上处于空闲状态。Vite 的资源模型让这一切运作得特别好。每个模块都有自己的 content-hashed chunk，所以对 billing 模块的改动只会使该 chunk 失效。回访用户下载的是 KB 级别的内容，而不是 MB 级别。

这就是我们认为前端应该被部署的方式：构建是快速的，资源是不可变且缓存友好的，底层的基础设施处理滚动更新、预览和路由，不需要你操心。你的前端框架应该为迭代速度而优化，你的基础设施应该让发布这些迭代变得无感。这就是我们为自己以及 Railway 上的每一个用户正在构建的体验。

## 为什么是现在

前端的迭代速度现在比以往任何时候都更重要。

之前需要 10 分钟以上的构建现在不到两分钟就完成了。Dev server 即时启动。路由变更在边界处进行类型检查。布局可以无需变通方案就进行组合。

从编写代码到将它呈现在用户面前，这中间的间隔就是瓶颈，而我们在这里做的一切——框架切换、边缘缓存、资源模型——都是为了缩短这个间隔。Vite + TanStack 让我们为一个前端变更几乎可以即时发布的世界做好了准备，而那就是我们正在朝着构建的世界。

核心观点：Railway 将整个生产前端从 Next.js 迁移到 Vite + TanStack Router，仅用两个 PR 就完成了 200+ 路由的零停机迁移。核心驱动力是 Next.js 的 Server-first 范式与 Railway 客户端驱动产品的根本错配，以及 10 分钟构建时间对高频迭代团队的严重拖累。迁移后构建时间降至 2 分钟以内，开发体验大幅提升。
